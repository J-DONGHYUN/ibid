# 기술 로드맵 — 동시성 · 정합성 · 조회 성능

> **이 문서 = 앞으로 할 기술 과제.** 지금 진행 중인 작업은 [`BACKLOG.md`](./BACKLOG.md).
> **목적**: 백엔드 기술 역량 증명. **기능 수가 아니라 깊이로 평가받는다** — 기능을 늘리지 않고, 이미 만든 것을 파고든다.

## 0. 원칙

### 축을 3개로 좁힌다

10개를 얕게 판 것보다 3개를 깊게 판 쪽이 강하다. 확장 항목은 세 축이 끝난 뒤에만 손댄다.

```
축 1. 동시성      같은 순간 여러 요청 → 락 · 원자연산 · 제약으로 순서를 만든다
축 2. 정합성      여러 단계 중간 실패 → 멱등성 · 보상 · Outbox로 되돌리거나 다시 시도한다
축 3. 조회 성능   대용량에서 느려짐 → 인덱스 · N+1 제거 · 캐싱

기반  측정        위 셋을 숫자로 증명하는 도구 (없으면 전부 주장에 그침)
```

### 모든 과제는 4단계 루프로 진행한다

*"비관적 락을 적용했습니다"* 는 **선택**만 보여준다. 아래 순서로 가야 **판단**이 남는다.

```
① 깨뜨린다   문제를 재현하는 테스트를 먼저 만든다 (락 없는 버전으로 재고를 음수로 만든다)
② 측정한다   before 숫자를 남긴다 (EXPLAIN 행수 · p95 · TPS · 실패율)
③ 고친다     대안을 2~3개 비교한다. 하나만 적용하고 끝내지 않는다
④ 기록한다   왜 그걸 골랐는지 근거와 함께 문서로 남긴다
```

### 완료 정의 (Definition of Done)

각 과제는 아래 셋이 모두 있어야 완료로 친다. 코드만 머지된 것은 완료가 아니다.

1. **문제를 재현하는 테스트** — 고치기 전 상태가 실제로 깨진다는 증거
2. **before / after 숫자** — 측정 조건(데이터 규모·동시 요청 수)까지 함께
3. **대안 비교가 담긴 문서** — 왜 다른 방법을 택하지 않았는지

> 시딩은 단순 반복 INSERT가 아니라 **배치 INSERT · `rewriteBatchedStatements` · 인덱스 생성 시점**까지 다루면 그 자체가 소재가 된다.

### PERF-1 결과 요약 (상세 → [`PERF_SEEDING.md`](./PERF_SEEDING.md))

| 발견 | 숫자 |
| --- | --- |
| JPA `saveAll`은 `IDENTITY` 전략 때문에 INSERT 배치가 걸리지 않는다 | 5,022 → 40,163 rows/sec (**8배**) |
| 처리량을 실제로 결정한 건 `batchUpdate`가 아니라 **드라이버가 SQL을 합쳐주는 것** | `rewriteBatchedStatements` off 7,640 → on 40,163 (**5.26배**). off일 때는 배치 크기를 5배 늘려도 2%만 변함 |
| 보조 인덱스에 **순차로 넣는지 무작위로 넣는지**가 12배를 만든다 | `product_tag`(순차) 97,964 vs `product_likes`(무작위+인덱스 2개) 8,302 rows/sec |

**확보된 before 숫자** — 이 위에서 축 3을 측정한다.

| 쿼리 | `EXPLAIN` | 실측(오버헤드 차감) |
| --- | --- | --- |
| `WHERE status='ON_SALE' ORDER BY created_at DESC LIMIT 16` | **`ALL` 풀스캔 + `filesort`** (798,124행) | **약 670ms** ← PERF-3 1순위 |
| `ORDER BY id DESC LIMIT 500000, 16` | `index` (500,016행 스캔) | 약 100ms ← PERF-6 |
| `WHERE id < ? ORDER BY id DESC LIMIT 16` (커서) | `range` + Backward index scan | 약 1ms |
| `COUNT(*) FROM product_likes WHERE product_id = ?` | `ref` + **`Using index`**(커버링) | 약 0ms |

## 축 1. 동시성

### 현황 — 이미 서로 다른 3가지 기법을 쓰고 있다

새로 만들 것이 거의 없다. **이미 한 선택을 근거와 숫자로 설명하는 작업**이 남았을 뿐이다.

| 문제 | 현재 기법 | 코드 |
| --- | --- | --- |
| 재고 차감 | **비관적 락** (`SELECT ... FOR UPDATE`) | `ProductRepository.findByIdForUpdate` |
| 찜 중복 | **DB 유니크 제약** + 409 응답 | `ProductLike` unique(user_id, product_id) |
| 조회수 | **Redis Lua 원자 연산** (`SET NX PX`) | `scripts/record-product-view.lua` |

> **핵심 질문**: "왜 셋을 다르게 풀었나?" — 이 하나로 면접 20분을 채울 수 있다.

### 과제

| ID | 작업 | 우선 | 산출물 |
| --- | --- | --- | --- |
| CONC-1 | **깨진 상태 재현** — 락 없는 재고 차감으로 동시 100요청 → 재고 음수/과판매를 테스트로 고정 | **P0** | 실패하는 테스트 |
| CONC-2 | **재고 차감 3안 비교** — 비관적 락 / 낙관적 락(`@Version`) / 조건부 UPDATE(`WHERE stock >= ?`) | **P0** | 처리량·실패율·재시도 횟수 표 |
| CONC-3 | **격리 수준 실험** — `READ COMMITTED` vs `REPEATABLE READ`에서 결과가 갈리는 지점 확인 | P1 | 재현 테스트 |
| CONC-4 | **찜 — 왜 락이 아니라 제약인가** 정리. 유니크 위반 → 409 변환 경로 포함 | P1 | 문서 절 |
| CONC-5 | **조회수 — 왜 DB가 아니라 Redis Lua인가** 정리 (기존 문서 보강) | P2 | `PRODUCT_VIEW_PROCESS.md` 갱신 |

**CONC-2 비교 축**

| 방식 | 처리량 | 실패 처리 | 유리한 상황 |
| --- | --- | --- | --- |
| 비관적 락 | 낮음 (직렬화) | 대기 후 성공 | 충돌 잦음, 실패 비용 큼 |

## 축 2. 정합성

### 현황 — 실탄이 이미 문서화돼 있다

[`PAYMENT_PROCESS.md §6`](./PAYMENT_PROCESS.md#6-알려진-이슈)에 **교과서적인 결함 5개**가 적혀 있다. 그중 §6-1은 동시성 문제가 정합성 사고로 번지는 완벽한 사례다.

> 재고 1개에 A·B 동시 결제 → A 성공 → **B는 토스 승인까지 끝난 뒤** 재고 차감에서 `SOLD_OUT` 예외 → 트랜잭션 롤백으로 주문·결제는 되돌아가지만 **토스 쪽 결제는 승인된 채 남는다.**
> **B는 돈을 냈는데 상품도, 주문도, 환불도 없다.**

그리고 **이벤트 아키텍처가 지금 반쪽이다.**

```
발행: InspectionService.java:59,66 → publishEvent(new InspectionPassed(orderId))
구독: 없음   ← src/ 전체에 @EventListener가 하나도 없다 (조회수 flush의 ContextClosedEvent 제외)
```

`CLAUDE.md`는 "payment가 구독"이라고 서술하지만 실제로는 아무도 듣지 않는다. **코드를 열어본 사람에게는 "이벤트 기반이라 써놓고 안 쓴다"로 읽히므로 가장 먼저 해소해야 한다.**

### 과제

| ID | 작업 | 우선 | 다루는 개념 |
| --- | --- | --- | --- |
| INTG-1 | **이벤트 소비자 만들기** — 발행만 하는 상태 해소. 문서와 코드 일치 | **P0** | 트랜잭션 경계 · `AFTER_COMMIT` |
| INTG-2 | **결제 멱등성** — 같은 주문에 confirm이 두 번 들어와도 한 번만 승인 (멱등 키) | **P0** | 멱등성 |
| INTG-3 | **보상 트랜잭션** — 승인 후 후속 실패 시 토스 결제 자동 취소 (`§6-1` 해결) | **P0** | 보상 · 외부 시스템 롤백 불가 |

| INTG-8 | **Outbox 패턴** — 커밋 직후 사망 시 이벤트 유실 방지 | P2 | Outbox · 이벤트 유실 |
| TRADE-5 | **수령확인 / N일 자동확정** | P2 | 스케줄러 기반 상태 전이 · 멱등 |

### 장애 주입으로 증명한다

정합성은 **정상 흐름으로는 증명되지 않는다.** 일부러 끊어야 한다.

- 토스 승인 직후 강제 종료 → 재기동 시 주문 상태는?
- 커밋 직후 강제 종료 → 이벤트는 소비됐나?
- 같은 confirm 요청 2회 동시 전송 → 두 번 승인되나?
- Redis flush 직전 종료 → 조회수는 유실되나?

각각에 대해 **고치기 전(깨짐) / 고친 후(복구)** 를 남긴다.

**산출물**: `docs/CONSISTENCY.md` + `PAYMENT_PROCESS.md` §6 갱신(해결 표시)

## 축 3. 조회 성능

### 현황 — 재료는 있는데 데이터가 없어 증명을 못 하고 있다

- 커서 페이지네이션 이미 구현 (`findByIdLessThanOrderByIdDesc`)
- 인덱스 설계 경험 이미 있음 — 찜수 조회용 `idx_product_likes_product` 추가로 `EXPLAIN` **9943행 → 20행**
- 복합 인덱스 **컬럼 순서** 함정도 이미 겪음 — `(user_id, product_id)` 순서라 `product_id` 단독 조회에 못 씀

### 과제

| ID | 작업 | 우선 | 다루는 개념 |
| --- | --- | --- | --- |
| PERF-2 | **N+1 제거** — 목록·마이페이지·검수 대기열. `fetch join` vs `@BatchSize` 비교 | **P0** | N+1 · 페치 전략 |
| PERF-3 | **인덱스 설계 + 실행계획 분석** — 커버링 인덱스, 복합 인덱스 컬럼 순서 | **P0** | `EXPLAIN` · 인덱스 |
| PERF-6 | **커서 vs 오프셋 비교** — 깊은 페이지(`OFFSET 500000`)에서 응답시간 격차 실측 | P1 | 페이지네이션 |
| CACHE-1 | **Redis 캐시 + 무효화 전략** — 상품 상세/목록. 상품 수정·삭제 시 무효화 | P1 | 캐시 정합성 |
| CACHE-3 | **스탬피드 방지 + 적중률 측정** — TTL 만료 순간 요청 폭주 | P2 | 캐시 운영 |
| PERF-5 | (선택) 커넥션풀(HikariCP) 튜닝 · 읽기 복제 분리 | P2 | 스케일 아웃 |

> **CACHE-1은 축 2와 만난다.** "캐시를 언제 지우나"는 곧 정합성 문제다. 캐시를 붙이는 것보다 **무효화**가 어렵다는 점을 문서에 남긴다.

**산출물**: `docs/QUERY_PERFORMANCE.md` — 실행계획 before/after · N+1 쿼리 수 · 페이지네이션 비교

## 이미 갖고 있으나 어필하지 않는 것

**새로 만들 필요 없이 설명만 정리하면 되는 것들.** 각 축 문서에 근거를 붙인다.

| 이미 한 것 | 팔 수 있는 지점 |
| --- | --- |
| **Testcontainers** MySQL·Redis + `@ServiceConnection` | H2로 테스트하다 운영에서 터지는 문제를 피한 선택 |
| **도메인 4계층 + 의존성 단방향** (`payment → order`) | 이벤트로 역방향 의존을 끊은 설계 |
| ~~**JWT 리프레시 토큰 회전**~~ | ⚠️ **아직 강점이 아니다** — `validate` → `SET`이 원자적이지 않아 동시 refresh에 경합이 있다. 프론트가 `401 → refresh → 재시도`라 병렬 요청 화면에서 실제로 터진다. **고친 뒤에 강점이 된다** → BACKLOG `AUTH-1` |
| **`@PublicApi` 인터셉터** | 경로 기반 제외는 HTTP 메서드를 구분 못 해 쓰기 API까지 열린다 — 보안 결함 예방 근거 |
| **S3 presigned URL** | 파일을 서버로 받지 않은 이유(대역폭·메모리) |
| **커서 페이지네이션** | 오프셋 대비 이점 (PERF-6에서 실측) |

## 진행 순서

```
Phase 0  측정 기반          PERF-1 시딩 · OPS-2 k6           ─ 1주   (없으면 아무것도 증명 못 함)
Phase 1  축 1 동시성        CONC-1~5                          ─ 1~2주 (재료 완비, 가성비 최고)
Phase 2  축 2 정합성        INTG-1~7                          ─ 2~3주 (깊이 최고, 핵심)
Phase 3  축 3 조회 성능     PERF-2·3·6 · CACHE-1              ─ 2주   (질문 빈도 최고)
Phase 4  확장               검색 / Outbox+Kafka / 배포        ─ 여력
```

**축 1을 먼저 두는 이유**: 코드가 이미 다 있어 실험과 문서가 대부분이라 가장 빨리 결과물이 나온다.
**축 2가 핵심인 이유**: 결제가 걸린 정합성이라야 "돈이 틀어진다"는 이야기가 된다. 다른 축으로는 이 무게가 안 나온다.

| ① | **결제 정합성을 범위 안에 들일지** | **들인다** — INTG-2·3·5가 여기 의존 | 축 2가 주문 상태기계·재고 복원·Redis write-back만 남아 **강도가 눈에 띄게 약해짐** |
| ② | **검색(ES)을 넣을지** | **확장으로 보류** | 넣으면 축이 4개가 되고 Phase 4가 본체가 됨 |
| ③ | **첫 이벤트 소비자를 무엇으로 할지** | **미정** — 알림(NOTI-2) / 검수→정산 / 검색 색인 | 검수→정산을 고르면 ①과 같은 결정이 됨. 이벤트가 **돈**을 움직여 정합성 이야기가 가장 강해짐 |

> ①과 ③은 사실상 하나의 결정이다.
