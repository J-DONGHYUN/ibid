#### DTL-4 상품 필드 확장 (진행 중)
- `tags` — `Tag` 엔티티 `@ManyToMany`(조인 테이블 `product_tag`), 같은 이름 태그는 find-or-create로 **재사용**. 모델 선택 근거는 [`FEATURE_SPEC.md`](./FEATURE_SPEC.md#23-상품-product)

- `shippingFee` — 0원=무료배송, 등록/수정 폼·상세 연동
- `feat/product-like`(#35)에서 갈라져 나온 브랜치 — **main 머지 완료**(#34 조회수 포함). `ProductDetailResponse`·`ProductService` 충돌은 조회수(`viewCount`·`visitorId`)를 살리는 방향으로 해결, 회귀 방지 단언 추가
- ⚠️ **미해결 리뷰 지적 있음** → 아래 `DTL-4+`. 특히 **`shippingFee`가 결제 총액에 합산되지 않음**

#### 코드 점검에서 새로 발견 (2026-08-10)

리뷰가 아니라 **동시성·정합성 표면을 훑다가** 나온 것들. 로드맵 축 1·2를 착수할 때 그대로 소재가 된다.

| ID | 작업 | 우선 | 근거 |
| --- | --- | --- | --- |
| **AUTH-1** | **리프레시 토큰 회전 경합 제거** | **P1** | `AuthService.refresh`가 `validate`(Redis 읽기) → `rotate`(같은 키에 `SET`)로 나뉜 **check-then-act**. 동시에 두 요청이 같은 old 토큰으로 통과한 뒤 나중 것만 남아 **먼저 받은 클라이언트의 토큰이 즉시 무효**가 된다. 프론트 정책이 `401 → refresh → 재시도`라 **병렬 요청 화면에서 실제로 발생**. 조회수에서 쓴 `SET NX`/Lua로 원자화 가능 |
| **IMG-1** | **S3 삭제를 트랜잭션 커밋 이후로** | **P1** | `ProductService.deleteImages`·`delete`가 `@Transactional` **안에서** `s3ImageUploader.delete`를 호출한다. S3 삭제 후 커밋이 실패하면 **파일은 없는데 DB에 URL이 남고**(깨진 이미지), 커밋 후 S3 실패하면 **고아 객체가 남아 스토리지 비용**이 계속 나간다 |
| IMG-2 | presigned 업로드 고아 객체 정리 | P2 | 클라이언트가 S3에 올린 뒤 `confirmImages`를 호출하지 않으면(이탈·네트워크 끊김) **DB에 기록 없는 파일이 영구히 남는다**. S3 Lifecycle 또는 대조 배치 필요 |
| AUTH-2 | 회원가입 이메일 중복 처리 방식 통일 | P2 | `existsByEmail` 선확인 → `save`의 check-then-act. 동시 가입 시 `Email`의 unique 제약이 막지만 응답이 의도한 `DUPLICATE_EMAIL`이 아닌 409로 나간다. **찜(DTL-2)에서는 "제약에 맡기고 throw만"으로 이미 정리했는데 여기만 옛 방식** |
| ORDER-1 | 주문 상태 전이에 락이 없는 근거 확인 | P2 | 재고는 `findByIdForUpdate`(비관적 락)인데 `confirmPaid`·`ship`·`complete`·`cancel`은 전부 `findById`(락 없음). 7상태 상태기계가 보호되지 않아 동시 전이 시 Lost Update 가능. **의도된 선택이면 근거를 남기고, 아니면 보호 추가** |

### 알림 (거래 상태 기반)

알림 자체가 목적이 아니라 **이벤트 기반 아키텍처의 정합성**을 보여주는 소재다(Spring `ApplicationEvent` + `@TransactionalEventListener(AFTER_COMMIT)`, 검수 이벤트와 동일 패턴). 화면 기능은 최소로 유지한다.

| ID | 작업 | 담당 | FE/BE | 기술포인트 |
| --- | --- | --- | --- | --- |
| NOTI-1 | `OrderPaid` 이벤트 발행 — 결제확정(`OrderService.confirmPaid`) 시 `(orderId, sellerId)` | 동현 | BE | 이벤트 발행·트랜잭션 경계 |
| NOTI-2 | 알림 도메인(`Notification`) + 구독자 → **판매자 "결제완료, 발송하세요" 알림** 생성 | 진호 | BE | 이벤트 구독·**멱등 소비** |
| NOTI-3 | 알림 조회/읽음 API — `GET /api/notifications` · `PATCH /{id}/read` | 진호 | BE | 이벤트 소비 결과 확인용(최소) |

> 접점(합의): `OrderPaid` 이벤트 계약 + 알림 조회 API 스펙.
> **핵심 질문**: `AFTER_COMMIT` 발행은 커밋 직후 서버가 죽으면 **이벤트가 유실된다**. 유실을 허용할지, Outbox로 막을지 결정 필요 → 정합성 트랙에서 다룬다.
> Defer: 실시간(SSE/푸시)·이메일·알림 설정·헤더 뱃지 UI.
