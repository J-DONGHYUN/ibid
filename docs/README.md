# 문서 지도

ibid 의 **정본 문서**가 어디에 있고, 둘이 다르게 말할 때 어느 쪽을 따르는지 정한다.
사람과 에이전트가 같은 문서를 읽는다.

## 폴더 구조

```
docs/
├── README.md                  이 파일. 문서 지도 · 정본 규칙 · ID 체계
├── 01-product/
│   ├── PRD.md                 무엇을 누구를 위해 만드는가. 범위와 하지 않는 것(NG)
│   ├── requirements.md        요구사항(ID)과 검증 기준. 검증 기준이 곧 테스트 목록
│   └── backlog.md             티켓(T) — 무엇이 끝났고 무엇이 남았나. 진행 상태의 정본
├── 02-design/
│   ├── domain-model.md        용어 · 애그리게이트 · 불변식(I) · 상태 전이표
│   ├── api.md                 엔드포인트와 인증 등급
│   └── adr/                   설계 결정 기록 (ADR-0001-*.md)
├── 03-convention/
│   ├── architecture.md        레이어와 의존 방향
│   ├── code.md                코드 작성 규칙
│   └── test.md                테스트 작성 규칙
├── 04-harness/
│   ├── harness.md             하네스 설계도. 무엇을 왜 강제하는가
│   ├── loop.md                루프 설계서. 작업 하나가 어떻게 시작해 어떻게 끝나는가
│   └── incidents.md           에이전트 사고와 처방 기록 (INC)
└── 05-records/
    ├── experiments/           측정·실험 기록 (EXP-01-*.md)
    └── qa/                    적대적 QA 시나리오와 발견 (QA-01-*.md)
```

**진행 상태의 정본은 `01-product/backlog.md` 다.** GitHub 이슈는 미리 만들지 않고, 티켓을 시작할 때 만든다 —
이슈는 계획을 게시하고 PR 이 닫는 **작업 기록**이다. 두 벌이 갈라지지 않도록 **상태는 루프만 바꾼다**
(시작하면 `🔄` 와 이슈 번호, PR 에서 `✅`).

## 정본 규칙

둘이 다르게 말할 때 따를 쪽을 먼저 정한다. 정하지 않으면 어긋난 자리마다
근거 없는 판단을 하게 된다.

| 무엇 | 정본 | 이유 |
|---|---|---|
| 무엇을 만드는가, 하지 않는가 | `01-product/` | 코드는 결정의 결과일 뿐 이유를 담지 못한다 |
| 규칙과 불변식 (무엇을 · 왜) | `02-design/` | 코드와 다르면 **코드가 버그이거나 문서가 낡은 것이다.** 추측하지 말고 사람에게 묻는다 |
| 구현 세부 (필드명 · 에러 코드 목록 · 설정값) | **코드** | 문서에 옮겨 적으면 두 벌이 된다. 문서는 코드 위치만 가리킨다 |
| 진행 상태 · 할 일 | `01-product/backlog.md` | 한 문서에서 끝난 것 · 남은 것 · 순서가 보여야 한다. 이슈는 시작할 때 만드는 작업 기록 |

요약하면 — **무엇과 왜는 문서가, 어떻게는 코드가 정본이다.**

## ID 체계

문서끼리, 그리고 문서와 코드·테스트가 ID 로 서로를 가리킨다.
**인용은 ID 나 절 제목으로 건다. 장 번호로 걸지 않는다** — 번호는 개정 때마다 밀린다.

| 접두어 | 무엇 | 정의하는 곳 | 예 |
|---|---|---|---|
| `NG-nn` | 하지 않는 것 (Non-Goal) | `01-product/PRD.md` | `NG-01` 결제·에스크로 없음 |
| `AU-nn` | 요구사항 — 인증 | `01-product/requirements.md` | `AU-01` 회원가입 |
| `PD-nn` | 요구사항 — 상품 · 찜 | 〃 | `PD-03` 상품 목록 조회 |
| `CH-nn` | 요구사항 — 채팅 | 〃 | `CH-01` 채팅방 열기 |
| `TR-nn` | 요구사항 — 거래 (예약 · 거래완료) | 〃 | `TR-01` 예약하기 |
| `NT-nn` | 요구사항 — 알림 | 〃 | `NT-01` 새 메시지 알림 |
| `T-nn` | 티켓 (작업 한 단위) | `01-product/backlog.md` | `T-04` 삭제 예정 도메인을 지운다 |
| `I-nn` | 불변식 | `02-design/domain-model.md` | `I-01` 예약 상대는 한 명이다 |
| `ADR-nnnn` | 설계 결정 | `02-design/adr/` | `ADR-0001` 채팅 실시간 전달 방식 |
| `EXP-nn` | 실험·측정 | `05-records/experiments/` | `EXP-01` 예약 동시 요청 처리 |
| `QA-nn` | 적대적 QA 시나리오·발견 | `05-records/qa/` | `QA-01` 교차 도메인 불변식 갭 |
| `INC-nn` | 에이전트 사고 | `04-harness/incidents.md` | `INC-01` |

**ID 는 한 번 쓰면 재사용하지 않는다.** 폐기된 요구사항은 지우지 않고 `폐기` 로 표시한다.
지우면 그 ID 를 인용한 테스트와 커밋이 가리킬 곳을 잃는다.

## 게이트 후보 표시

규칙을 적을 때 **기계가 판정할 수 있는 것**에는 `[G]` 를 붙인다.
하네스를 설계할 때 이 표시를 모아 게이트(ArchUnit · 테스트 · 훅)로 옮긴다.

```
- [G] 거래완료된 상품은 예약중으로 바꿀 수 없다   → 상태 전이 테스트로 옮길 수 있다
- 채팅 실시간 전달은 ○○ 방식으로 한다 (ADR-0001)  → 이유는 판정할 수 없다. 컨텍스트로만 둔다
```
