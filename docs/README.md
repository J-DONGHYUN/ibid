# 문서 인덱스

`ibid` — 일반 중고 거래 + 검수 에스크로 이커머스. 전 거래 배송 · 강제 검수 · 직거래/채팅 없음.
**포트폴리오 프로젝트**이므로 동작하는 기능뿐 아니라 **기술적 성장(설계·동시성·이벤트기반·인프라·트러블슈팅)** 을 보여주는 것을 우선한다.

## 어떤 문서를 언제 읽나

읽는 순서는 **왜 → 무엇 → 언제 → 어떻게** 다.

| | 문서 | 답하는 질문 | 이럴 때 읽는다 |
| --- | --- | --- | --- |
| **왜** | [PRODUCT_PLAN.md](./PRODUCT_PLAN.md) | 누구를 위해 무엇을 만드는가 | 처음 합류했을 때 · 범위를 정할 때 |
| **무엇** | [FEATURE_SPEC.md](./FEATURE_SPEC.md) | 기능이 어떻게 동작해야 하는가 | **기능 작업 전 필독** — 플로우·담당 경계 |
| | [API.md](./API.md) | 어떤 엔드포인트가 있는가 | 프론트 연동 · API 추가 시 |
| **언제** | [BACKLOG.md](./BACKLOG.md) | **지금** 무엇을 하는가 | 다음 작업을 고를 때 · 진행 상태 확인 |
| | [ROADMAP.md](./ROADMAP.md) | **앞으로** 어떤 기술을 파는가 | 축(동시성·정합성·조회 성능)과 완료 기준 확인 |
| **어떻게** | [TEST.md](./TEST.md) | 테스트를 어떻게 쓰는가 | 테스트 작성 전 — 계층·네이밍·Fixture 규칙 |
| | [PAYMENT_PROCESS.md](./PAYMENT_PROCESS.md) | 결제가 실제로 어떻게 도는가 | 결제 흐름을 건드릴 때 · 알려진 결함 확인 |
| | [PRODUCT_VIEW_PROCESS.md](./PRODUCT_VIEW_PROCESS.md) | 조회수가 실제로 어떻게 도는가 | Redis 카운터·Lua·write-back 설계 근거 |
| | [PERF_SEEDING.md](./PERF_SEEDING.md) | 대량 더미데이터를 어떻게 넣는가 | 성능 측정 전 데이터 준비 · 시딩 방식 비교 근거 |

프로젝트 구조·명령어·도메인 계층 규칙은 저장소 루트의 [`CLAUDE.md`](../CLAUDE.md)에 있다.

## 문서 성격

- **PRODUCT_PLAN / FEATURE_SPEC / API** — 규격. "이렇게 되어야 한다"
- **BACKLOG** — 상태. 진행하면 계속 바뀐다
- **ROADMAP** — 방향. 기술 축 3개와 각 과제의 완료 정의(재현 테스트 · 숫자 · 대안 비교)
- **TEST** — 컨벤션. 팀 합의
- **`*_PROCESS`** — **구현 심화 + 설계 근거**. "왜 이렇게 짰는가"를 남긴 문서로, 사실상 ADR(Architecture Decision Record)에 해당한다. 리뷰어에게 가장 값나가는 문서군

## 갱신 규칙

- 기능을 추가·변경하면 **FEATURE_SPEC.md**와 **BACKLOG.md**를 함께 갱신한다
- 엔드포인트가 바뀌면 **API.md**도 갱신한다
- **진행 상태는 BACKLOG.md 한 곳에서만** 관리한다 — 두 군데에 두면 반드시 어긋난다 (`MVP.md`를 흡수한 이유)
- **지금 하는 일 = BACKLOG, 앞으로 할 일 = ROADMAP.** 로드맵 항목을 착수하면 BACKLOG로 끌어온다
- 설계 판단이 갈렸던 지점은 `*_PROCESS.md`에 **근거와 함께** 남긴다. 결론만 적으면 나중에 되돌릴 때 이유를 잃는다

## 구조 정책

폴더 없이 **flat**하게 둔다. 문서가 8~9개 규모에서 폴더를 나누면 1~2개짜리 폴더만 생겨 탐색이 나아지지 않는다.
아래 조건에 닿으면 그때 나눈다.

- `*_PROCESS.md`가 **3개째** → `docs/design/` (또는 `docs/adr/`)로 묶는다
- 전체 문서가 **12개** 초과 → 재검토
