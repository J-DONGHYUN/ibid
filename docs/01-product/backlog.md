# 백로그

**무엇이 끝났고, 무엇이 진행 중이고, 무엇이 남았는지**의 정본이다. 티켓 하나 = 이슈 하나 = PR 하나.

## 쓰는 법

```
"T-04 시작"                  → 이 문서의 T-04 로 이슈를 만들고 루프를 시작한다
"삭제 예정 도메인 지우기 시작"   → 제목으로 찾아 같은 흐름
"티켓: 가격 정렬 추가하자"      → 이 문서에 없으면 티켓을 추가하고 같은 흐름
```

- **이슈는 미리 만들지 않는다.** 티켓을 시작할 때 이 문서의 목표 · 완료 조건으로 이슈를 만든다 (`ticket` 스킬 [0])
- **상태는 루프가 바꾼다.** 시작하면 `🔄` 와 이슈 번호를, PR 에서 `✅` 를 적는다. PR 이 머지되면 완료다
- 순서는 표의 위에서 아래가 기본이다. **선행이 `✅` 가 아니면 시작하지 않는다**

| 상태 | 뜻 |
|---|---|
| ⬜ | 할 일 |
| 🔄 | 진행 중 — 이슈가 있고 루프가 돌고 있다 |
| ✅ | 완료 — PR 머지 |
| ⏸ | 보류 — 이유를 상세에 적는다 |

종류가 **결정**인 티켓은 코드를 짜지 않는다. 에이전트가 선택지를 정리하고, **사람이 정하고**, ADR 을 `채택` 으로 바꾼다.

### T-04 삭제 예정 도메인(order · payment · inspection)을 지운다

- **이슈 제목**: `chore: 삭제 예정 도메인(order · payment · inspection)을 지운다`
- **목표**: 이전 제품(검수 에스크로 배송 거래)의 도메인이다. 새 제품에 없고, 동결 기록의 대부분을 차지한다 (PRD 「현재 코드와의 차이」 · `NG-01` · `NG-02` · `NG-04`)
- **완료 조건**
  - order · payment · inspection 패키지와 그 테스트가 없다
  - 다른 코드가 이 셋을 참조하지 않는다 (`ControllerTestSupport` 의 mock 포함)
  - 전체 테스트가 통과한다
  - 동결 기록이 줄어들고, 늘어난 것은 없다 (`SourceRulesTest` 목록 포함)
  - `CLAUDE.md` 「이행기」 표와 `api.md` 「사라질 엔드포인트」 가 갱신된다
- **참고**
  - **첫 루프 티켓.** 계획 게시 후 `src/` 수정이 통과하는 경로를 여기서 처음 확인한다

### T-05 상품에서 재고 · 배송비 · PENDING 을 지운다

  - `PATCH /api/products/{id}/on-sale` 이 없다
  - `ErrorCode` 에 T-04 가 남긴 주문 · 결제 코드(`ORDER_*` 6개 · `PAYMENT_*` 4개)와 섹션 주석이 없다 (`INC-04`)

### T-30 guard-protected 의 오탐을 없앤다

- **이슈 제목**: `chore: guard-protected 의 오탐을 없앤다`
- **목표**: 리다이렉션(`2>&1`)과 heredoc 본문 속 단어 때문에 필요 없는 승인이 떴다 (`INC-03`). 쓰기 기호와
  보호 경로를 명령 전체에서 따로 찾지 말고 **쓰기 대상**이 보호 경로인지 본다. 같은 판정을 `guard-plan` 도 쓰게 한다
- **완료 조건**
  - `2>&1` · `>&2` · `>/dev/null` 은 쓰기로 보지 않는다
  - heredoc 본문(`<<'EOF'` 아래)은 검사하지 않는다
  - **쓰기 대상**이 보호 경로일 때만 `ask` 한다
  - 승인 창 메시지에 **걸린 파일 · 걸린 명령 · 승인/거절 기준**을 보여준다. 에이전트용 지시가 아니라 사람이 읽는 문장으로 쓴다
  - **쓰기 대상을 찾는 판정을 한 곳에 두고 두 훅이 같이 쓴다.** `guard-plan` 도 같은 방식으로 Bash 쓰기를 판단해,
    `./gradlew test 2>&1 | grep src/` 같은 읽기(리다이렉션은 stderr, `src/` 는 grep 인자)를 막지 않는다
  - 오탐 탐침(통과): INC-03 의 두 명령 — `… 2>&1 | tail … wc -l …/archunit-store/…`, `cat > pr-71.md <<'EOF' … archunit-store …`
  - 미탐 탐침(여전히 `ask`): heredoc 이 보호 파일에 쓰기(`cat > build.gradle <<'EOF'`) · `2> build.gradle` · `>>` ·
    `tee` · `cp`/`mv` 의 도착지 · `&&` 로 이어진 두 번째 명령 · 따옴표로 감싼 경로. 그리고 기존 막는 경로(`sed -i` ·
    리다이렉션으로 `build.gradle` · `git checkout` 으로 보호 파일)도 여전히 `ask`
- **참고**: 막는 경로가 줄어들면 안 된다. 오탐 제거와 미탐 증가를 같이 확인한다

### T-46 조회수 플러시 중 DB 실패로 조회수가 사라지지 않게 한다

- **완료 조건**

- **참고**: 선택지는 "읽고 → 반영 → 성공하면 차감" 또는 "실패하면 되돌려 놓기". 어느 쪽이든 새 조회와 경합하는 자리가 생기므로 동시성 테스트를 같이 쓴다

### T-50 Redis 가 멈추거나 내려갔을 때 로그인 · 토큰 재발급이 어떻게 되는지 실측한다

- **이슈 제목**: `test: Redis 장애 때 로그인 · 토큰 재발급 동작을 실측한다`
- **목표**: `T-45` 의 `spring.data.redis.timeout`(1초)은 Redis 를 쓰는 모든 곳에 적용된다. 인증의 refresh 토큰 저장(`RefreshTokenRedisRepository`)은 조회수와 달리 **예외를 삼키지 않고 던진다.** Redis 가 멈추면 로그인이 60초 걸린 뒤 실패하던 것이 1초 안에 실패하게 될 것으로 **추정**하지만 재지 않았다 (`T-45` 독립 리뷰 🟡)

  - Redis 무응답(`docker pause`)과 연결 거부(컨테이너 stop) 두 경우에서 `AuthService.login` · `refresh` · `logout` 의 응답 시간과 결과(성공 · 어떤 예외 · 클라이언트 응답 코드)를 잰다

  - 결과를 `QA-02` 에 덧붙이고, 결함이 있으면(예: 500 으로 새는 것) 고칠 티켓을 `⬜` 로 둔다

- **결과 (2026-10-05)**: 재서 확인했다 — 무응답(`docker pause`)에서 로그인 500 · 1070ms, 재발급 500 · 1008ms, 로그아웃 500 · 1009ms, 연결 거부에서 80 · 15 · 3ms. 셋 다 500 이고 재발급 · 로그아웃은 refresh 쿠키를 지우지 않는다. 정상 Redis 에서 동시 로그인 300건 실패 0건, 최대 286ms. 의도 여부는 `T-55` 로 올렸다. 한 번의 로컬 측정이고 로그인 한 종류의 부하다 (`QA-02` `[QA-B.5]`)
- **참고**: 이 티켓은 제품 코드를 고치지 않는다. 로그인이 Redis 에 막히는 것이 의도인지(토큰 저장은 필수) 아니면 격리해야 하는지는 측정 뒤 사람이 정한다

### T-51 삭제 때 S3 에 남는 옛 형식 · 고아 이미지 객체의 정리 전략을 정한다 · 결정

### T-52 쓰기 경로의 상품 조회를 삭제 제외 전용 조회로 모으고 게이트를 건다

### T-54 동결 저장소가 규칙 변경과 함께 커밋되지 않으면 CI 가 실패하게 한다

- **이슈 제목**: `chore: 동결 저장소가 규칙 변경과 함께 커밋되지 않으면 CI 가 실패하게 한다`
- **목표**: `T-52` 를 하다 발견했다. `FreezingArchRule` 은 규칙 문구로 항목을 찾는데, 커밋된 저장소에 **현재 규칙 문구의 항목이 없으면 처음 보이는 순간 현재 위반을 전부 받아들여 통과한다.** `allowStoreCreation=false` 는 저장소 파일 전체가 없을 때만 막는다 (`ADR-0010` 은 이를 보장하는 것처럼 적었다). 그래서 규칙을 고치고 저장소를 커밋하지 않으면 그 규칙은 CI 에서 열린다
- **증거 (2026-10-05)**: 커밋된 `main` 의 깨끗한 체크아웃에 `common` → `product` 의존 클래스를 넣고 `architectureTest` 를 돌리면 **통과**했다 (`BUILD SUCCESSFUL`). 위반은 새로 만들어진 항목 파일에 들어가 있었다. 정합 커밋(`notification` 레이어 규칙 항목을 커밋) 뒤 같은 탐침은 `DOMAIN_DEPENDENCY_DIRECTION` 으로 **실패**했다. 이 구멍은 `T-25`(커밋 `6f9dedb`, 2026-10-02)가 `notification` 레이어 규칙 줄을 더한 뒤 저장소 변경이 커밋되지 않아 생겼다(저장소는 09-30 에 마지막으로 커밋됐다). 10-02 부터 10-05 까지 3일간 작업 트리의 미커밋 변경으로만 남아 있었다
- **완료 조건**
  - 테스트(또는 CI 단계)가 실행 뒤 `src/test/resources/archunit-store/` 가 **바뀌었으면 실패**한다. 예: CI 에서 테스트 뒤 `git diff --exit-code src/test/resources/archunit-store` 와 새 파일 검사. 래칫이 줄어드는 변경도 커밋해야 하므로 "저장소가 바뀜 = 커밋 안 한 상태" 로 같이 잡는다
  - **탐침**: 규칙 문구를 바꾸고 저장소를 커밋하지 않은 PR 이 CI 에서 실패한다. 정합한 PR 은 통과한다
  - 로컬에서도 같은 판정을 하는 방법을 정한다 (`gate-on-stop` · 게이트 테스트 중 구현에서 정한다)
  - `harness.md` 「알려진 구멍」 의 해당 항목이 해결로 바뀐다
- **결과 (2026-10-05)**: `ci.yml` 이 아니라 `build.gradle` 의 모든 `Test` 태스크에 걸었다 — 로컬 게이트와 CI 가 같은 판정을 한다. 실패 기준은 "새 파일 또는 늘어난 줄"이고 줄어드는 것은 허용한다(원래 안은 "바뀌면 실패" 였으나, 감소까지 막으면 위반을 고칠 때마다 커밋을 강요한다). 탐침: 고치기 전 `BUILD SUCCESSFUL` → 고친 뒤 `BUILD FAILED`, 정합 체크아웃 통과, 가짜 줄 추가는 ArchUnit 이 지워 통과, 새 규칙의 첫 실행은 실패하고 저장소 변경을 스테이징하면 통과
- **참고**: `.github/workflows/ci.yml` 은 하네스의 보호 대상이라 수정에 사람의 승인이 든다. `ADR-0010` 의 동결 방식 자체를 바꾸는 것은 아니다(결정은 그대로, 보장 범위를 맞춘다)
