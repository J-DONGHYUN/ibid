# PRD

ibid 가 **무엇을, 누구를 위해** 만드는지와 **하지 않는 것**을 정한다.
기능 단위 정의와 검증 기준은 `requirements.md` 에 있다.

## 한 줄 정의

**동네에서 만나 거래하는 중고 전자기기 마켓.**
판매자가 전자기기 전용 정보로 상품을 올리고, 구매 희망자와 1:1 채팅으로 약속을 잡아
직접 만나서 거래한다.

## 프로젝트 목표

이 프로젝트는 서비스 운영이 아니라 **개발 방식과 기술의 증명**이 목적이다.

1. **하네스 루프 엔지니어링** — 컨텍스트를 설계하고, 하네스로 강제·판정하고,
   에이전트 루프로 기능을 개발한다. 루프가 새는 곳을 기록하고 하네스를 개선한다
   (`04-harness/`)
2. **동시성 · 정합성** — 한 상품을 두고 여러 사람이 동시에 움직이는 자리
   (예약, 거래완료, 채팅방 생성)에서 상태가 깨지지 않게 한다
3. **비동기 · 메시징** — 채팅과 알림을 Kafka 기반 이벤트로 흘린다

사용자 수·매출 같은 제품 지표는 목표가 아니다.

## 문제 정의

중고 전자기기는 상태 편차가 커서, 일반 중고 거래 앱에서는 **채팅으로 같은 질문이
반복된다.** "배터리 몇 %예요?", "구성품 다 있어요?", "액정 멍 있나요?".
정보가 부족한 글은 구매자가 판단하지 못하고, 판매자는 같은 답을 반복한다.

→ **전자기기 전용 정보를 등록 단계에서 구조화해 받는다.** 채팅은 확인과 약속에 쓴다.

## 사용자

한 계정이 판매자와 구매자를 모두 한다. 상품 기준의 역할 이름일 뿐 계정 종류가 아니다.

| 역할 | 원하는 것 |
|---|---|
| 판매자 | 쓰던 전자기기를 빨리, 같은 질문 반복 없이 판다 |
| 구매자 | 상태를 미리 알고, 판매자와 바로 대화해 가까운 곳에서 산다 |

## 핵심 거래 흐름

```
판매자: 상품 등록 (판매중)
          │
구매 희망자 A, B, C … : 각자 판매자와 1:1 채팅
          │
판매자: 채팅 상대 중 한 명을 골라 예약중으로 바꾼다
          │           └── 약속이 깨지면 예약 해제 → 다시 판매중
          │
만나서 거래
          │
판매자: 거래완료 (구매자를 지정)
```

- **상품 상태는 판매중 → 예약중 → 거래완료** 셋이다. 예약중에서 판매중으로 되돌릴 수 있다
- **한 상품에 채팅방이 여러 개** 생긴다. 채팅방은 (상품, 구매 희망자) 쌍마다 하나다
- **예약과 거래완료의 상대는 그 상품의 채팅 상대 중에서** 고른다
- **돈은 플랫폼을 지나지 않는다.** 만나서 직접 주고받는다

## 범위

### In

- 회원 인증
- 상품: 전자기기 전용 정보(모델 · 용량 · 배터리 성능 · 구성품 · 하자 등) 등록 · 수정 · 삭제 · 목록 · 상세 · 이미지
- 찜
- 1:1 채팅: 상품당 여러 채팅방, 실시간 전달, 읽음 표시
- 거래 상태: 예약 · 예약 해제 · 거래완료
- 알림: 새 채팅 메시지

### 하지 않는 것 (NG)

에이전트는 일반적인 이커머스를 "완성"하려 드는 경향이 있다. 아래는 **일부러 만들지 않는다.**

| ID | 하지 않는 것 | 이유 |
|---|---|---|
| `NG-01` | 결제 · 에스크로 · 정산 | 돈은 만나서 직접 주고받는다. PG 연동을 두지 않는다 |
| `NG-02` | 검수 · 배송 | 직거래가 전제다 |
| `NG-03` | 수량(재고) 판매 | 게시글 하나 = 물건 하나. 재고 수량 개념을 두지 않는다 |
| `NG-04` | 장바구니 · 주문서 | 거래는 채팅과 예약으로 성립한다 |
| `NG-05` | 대용량 조회 성능 · 부하 테스트 | 이번 프로젝트의 기술 목표가 아니다 |
| `NG-06` | 경매 · 입찰 | 고정가로 올리고 채팅으로 조율한다 |

## 현재 코드와의 차이

이 PRD 는 **이전 제품(검수 에스크로 배송 거래)에서 방향을 바꾼 것**이다.
코드에는 이전 제품이 남아 있고, 아래는 GitHub Issues 로 옮겨 루프로 정리한다.

| 남아 있는 것 | 이 PRD 기준 |
|---|---|
| `payment` (Toss 연동) | 지운다 (`NG-01`) |
| `inspection` (검수) | 지운다 (`NG-02`) |
| `order` (주문 7상태) | 지운다. 거래 상태는 상품의 예약 · 거래완료로 대체 (`NG-04`) |
| `product` 의 재고 · 비관적 락 | 재고를 지운다 (`NG-03`). 동시성 제어는 예약 · 거래완료 전이로 옮겨간다 |
| `frontend` (Next.js) | 유지한다. 이전 흐름 화면은 새 흐름에 맞춰 바꾼다 |

## 남은 결정

- **동네(위치)**: 동네 인증 · 거리 기반 목록을 넣을지. 넣으면 조회 조건이 크게 바뀐다
- **거래 후기 · 매너 평가**: 거래완료 뒤 서로 평가할지
- **가격 제안**: 구매자가 가격을 제안하는 기능을 둘지
- **채팅 실시간 전달 방식**: WebSocket(STOMP) · SSE 중 무엇으로 할지 → ADR 로 정한다
