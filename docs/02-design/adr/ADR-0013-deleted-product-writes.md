# ADR-0013 삭제된 상품에 대한 쓰기 연산의 기준

- 상태: **제안** (2026-10-05) — 사람이 정한다
- 관련: `PD-06` · `PD-07` · `PD-08` · `CH-01` · `TR-01` · `TR-03` · `I-09` · `ADR-0011`
- 이 ADR 이 정해지기 전에는 `T-39` · `T-42` 를 시작하지 않는다 (`CLAUDE.md`: 제안 상태 ADR 에 걸린 요구사항은 구현하지 않는다)

## 맥락

`ADR-0011` 은 소프트 삭제(`deletedAt`)를 채택하면서 **조회에서 숨길지 보여줄지**를 정했다
("숨길 조회에만 `deletedAt IS NULL` 을 건다"). **쓰기는 정하지 않았다.**

`QA-01`(2026-10-03)이 그 공백을 재현했다.

- 삭제한 상품이 `ON_SALE → RESERVED → SOLD` 를 끝까지 통과한다. 최종 상태 `status=SOLD deletedAt=true soldBuyerId=20` (`QA-1.1` · `1.2`)
- 삭제 · 거래완료된 상품에 새 채팅방이 열린다 (`QA-1.3` · `1.4`, `CH-01` 이 막으라고 한 것)
- 삭제된 상품을 찜할 수 있고, 읽히지 않는 찜 행이 쌓인다 (`QA-1.5`)
- 반면 **메시지 전송은 막힌다** (`I-09`, `QA-1.6`)

원인은 규칙이 연산마다 손으로 들어가 있어서 **들어간 곳만 막힌다**는 것이다. 엔티티의 상태 가드(`reserve` 는 `ON_SALE`,
`complete` 는 `SOLD` 가 아닐 것)는 `status` 만 알고, `deletedAt` 은 `status` 와 **다른 축**이라 막지 못한다.
`domain-model.md` 의 전이표에도 `deletedAt` 축이 없다.

이 결정은 ADR 기준에 걸린다 — 흔한 방법(연산마다 검사 추가)이 같은 결함을 되풀이할 수 있고, 대안이 여럿이며,
규칙을 흩뿌린 뒤에는 걷어내기 비싸다.

## 현재 동작 (2026-10-05, 코드로 확인)

삭제된 상품에 대해 각 연산이 지금 어떻게 동작하는가.

| 연산 | 지금 | 근거 |
|---|---|---|
| 목록 · 상세 조회 | 숨김 (상세 404) | `ProductService.getProducts` · `getProduct` |
| 수정 · 이미지 발급 · 확정 · 삭제 · 재삭제 | 막힘 (404) | `ProductService.findOwnedProduct` 의 `isDeleted` 필터 |
| 예약 · 예약 해제 · 거래완료 | **새어 나감** (성공) | `ReservationService` · `CompletionService` 가 삭제를 안 본다 |
| 새 채팅방 열기 | **새어 나감** | `ChatRoomService.open` 이 존재만 본다 |
| 기존 채팅방에 메시지 전송 | 막힘 (409 `PRODUCT_DELETED`) | `ChatMessageService.send` (`I-09`) |
| 기존 채팅방의 메시지 · 방 목록 조회, 읽음 처리 | 허용 | 의도 (`ADR-0011`: 채팅방은 남는다) |
| 찜하기 | **허용** (읽히지 않는 행이 남음) | `ProductLikeService.like` 가 `existsById` 만 본다 |
| 찜 취소 · 찜 여부 · 찜 수 | 허용 | 삭제를 안 본다 |
| 관심 목록 | 숨김 | `ProductLikeService.myLikedProducts` |
| 판매 · 구매 내역 | 포함 | 의도 (`ADR-0011`: 내역은 보존) |

삭제 여부를 보는 곳은 **다섯 군데뿐**이다 — `ChatMessageService.send`, `ProductService`(`findOwnedProduct` · `getProduct`),
`ProductLikeService.myLikedProducts`, 목록 쿼리 두 개.

## 제안하는 원칙

> 삭제는 상품을 화면에서 치우고 **새 거래 · 새 관계를 만들지 못하게** 한다.
> 이미 맺어진 것(채팅방 · 거래 내역)은 읽을 수 있다.

이 원칙으로 연산을 셋으로 나눈다.

- **막는다** — 삭제된 상품의 상태를 바꾸거나, 삭제된 상품에 새로 무언가를 붙이는 쓰기: 예약 · 예약 해제 · 거래완료 · 새 채팅방 열기 · 메시지 전송 · 수정 · 이미지 변경 · 재삭제 (+ 찜하기는 질문 2)
- **허용한다 (읽기)** — 이미 맺어진 관계를 보는 조회: 기존 채팅방의 메시지 · 방 목록, 판매 · 구매 내역
- **허용한다 (정리)** — 이미 있는 것을 치우거나 상태를 따라가는 것: 찜 취소, 채팅방 읽음 처리

## 선택지 — 어디서 막을까 (질문 3)

| | A. 서비스마다 `isDeleted()` 검사 | B. 쓰기 경로 전용 조회 + 게이트 | C. 엔티티 전이 가드가 `deletedAt` 도 봄 |
|---|---|---|---|
| 방식 | 막을 서비스마다 상품을 읽은 뒤 `isDeleted()` 를 확인한다 (지금 `ChatMessageService.send` 방식을 넓힌다) | 쓰기 경로가 상품을 얻는 조회를 하나로 모은다 — 삭제를 제외하는 `findActiveById`. 읽기 경로(내역 · 채팅방 목록)는 `findById` 를 그대로 쓴다. `findById` 를 쓰는 곳을 ArchUnit 으로 세어 새로 늘지 못하게 한다 (`ADR-0010` 의 동결 방식) | `Product.reserve` · `complete` 가 `deletedAt` 도 확인해 던진다. 전이표에 `deletedAt` 축이 생긴다 |
| 잊으면 | 같은 결함이 다시 생긴다 (이번 결함의 원인이다). 테스트가 유일한 안전망 | 게이트가 새 `findById` 호출을 막아 잡는다. 단 `findById` 자체는 여전히 쓸 수 있다 | 전이는 못 샌다. 채팅방 열기 · 찜은 엔티티가 닿지 않아 별도 처리가 필요하다 |
| 막는 범위 | 연산마다 넣은 곳 | 쓰기 경로 전체 (예약 · 거래완료 · 새 채팅방 · 찜 · 메시지) | 상태 전이만 (예약 · 해제 · 거래완료 · 수정) |
| 변경량 | 작다 (서비스 4~5곳) | 중간 (조회 메서드 1개 + 서비스 4~5곳 + 게이트 규칙 1개) | 중간 (엔티티 + 전이표 + 전이마다 테스트 한 칸) |
| 문서 | 이 ADR 만 | 이 ADR + 게이트 설명 (`harness.md`) | 이 ADR + `domain-model.md` 전이표 + 불변식 |

**이미 기각된 것** — 다시 제안하지 않는다.

- **전역 필터(`@SQLRestriction`)**: `ADR-0011` 이 기각했다. 거래 내역 · 채팅방은 삭제된 상품을 읽어야 해서 필터를 끄는 우회가 늘어난다
- **`DELETED` 를 `status` 의 한 값으로**: 거래완료 상품도 삭제할 수 있고 삭제해도 내역에는 `SOLD` 로 남아야 하므로 한 필드에 담을 수 없다 (`ADR-0011`: 거래완료 상품 삭제 허용)

## 결정할 질문

1. **막을 쓰기의 범위** — 위 원칙대로 "상태를 바꾸거나 새로 붙이는 쓰기는 모두 막는다"로 할까, 거래 상태 쪽만 막을까
2. **찜** (`QA-1.5`, 요구사항에 답이 없다) — 삭제된 상품을 찜하지 못하게 할까, 지금처럼 허용할까
3. **어디서 막을까** — 위 A · B · C 중 무엇
4. **막았을 때 응답** — 지금은 두 방식이 섞여 있다: 수정 · 상세는 404 `PRODUCT_NOT_FOUND`, 메시지 전송은 409 `PRODUCT_DELETED`

## 결정 기준

- **같은 결함이 다시 생기지 않는가** — 규칙을 한 곳에 모으고 잊었을 때 기계가 잡는 쪽이 낫다
- **되돌리기 쉬운가** — 서비스에 흩뿌린 검사는 나중에 한 곳으로 모으기 번거롭다
- **삭제 사실을 새 쓰기가 드러내는가** — 404 는 "없는 것처럼", 409 는 "삭제됐다"고 알려 준다. 목록 · 상세와 일관된 쪽은 404 다
- **기존 채팅방은 보이므로** 그 안의 쓰기가 막힌 이유는 알려 주는 편이 낫다

## 에이전트의 권고 (결정이 아니다)

사람이 정한다. 아래는 조사한 근거에 따른 의견이다.

1. **원칙대로 막는다.** "새로 붙이지 않는다"가 한 문장이라 예외 목록이 짧다 (예외: 찜 취소 · 읽음 처리)
2. **찜도 막는다.** 읽히지 않는 행이 쌓이는 것은 이득 없이 비용만 있고, 원칙과도 맞다. 찜 취소는 허용해 이미 있는 찜을 치울 수 있게 한다. 영향: `PD-07` 에 한 줄, `DeletedProductLikeTest` 단언 변경
3. **B.** 이번 결함의 원인이 "규칙이 흩어져 잊힌 것"이라 같은 방식(A)을 넓히면 재발한다. C 는 전이만 닿고 채팅방 열기 · 찜을 못 닿아 B 와 함께 써야 하는데, 그렇다면 B 만으로 충분하다. B 의 비용은 중간이고 게이트가 이 프로젝트의 방식이다
4. **상품을 직접 가리키는 요청(예약 · 거래완료 · 새 채팅방 · 찜)은 404, 이미 있는 채팅방 안의 쓰기(메시지)는 409 `PRODUCT_DELETED` 를 유지한다.** 상세 · 수정이 이미 404 라 일관되고, 방이 보이는 메시지 전송은 이유를 알려 주는 쪽이 낫다

## 이 결정이 정하지 않는 것

- **예약중인 상품을 삭제하면** `RESERVED` 로 동결된다 — 예약 상대에게 알리거나 자동으로 해제하지 않는다. 지금도 그렇고 이 ADR 이 바꾸지 않는다. 문제가 되면 별도 질문으로 올린다
- 판매 내역에 삭제한 상품이 나오는 것은 `ADR-0011` 의 의도다
- 이미지 정리는 `T-51`
