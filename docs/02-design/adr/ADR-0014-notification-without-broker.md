# ADR-0014 알림 전달에서 메시지 브로커를 걷어낸다

- 상태: **채택** (2026-11-02, 사람) — 스프링 애플리케이션 이벤트 · 커밋 후 전달 · 동기 저장
- 대체: `ADR-0009`(RabbitMQ · 커밋 후 발행)
- 관련: `I-11` · `NT-01` · `NT-02` · `NT-03` · `ADR-0007`

## 맥락

`ADR-0009` 로 RabbitMQ 를 들였다. 운영해 보니 큐가 주는 것이 쓰이지 않는다.

- **소비자가 하나**다. 알림 행을 DB 에 INSERT 하는 것 하나뿐이고, pub/sub 으로 갈라질 곳이 없다
- **처리가 가볍다.** 로컬 DB INSERT 한 건이라 요청 경로에서 떼어낼 만큼 무겁지 않다.
  오히려 발행이 네트워크 왕복이라 큐를 거치는 쪽이 더 걸릴 수 있다
- **수평 확장 계획이 없다.** 버퍼링도 소비자 확장도 지금 필요가 없다
- 재시도는 되레 위험했다 — 소비 실패 시 재배달 상한도 dead-letter 큐도 없어
  독약 메시지 한 건이 3초에 11,705회 재배달됐다 (`QA-A.1`). 고치려면 새 인프라 설정이 또 는다

그 대가로 **인프라 하나와 실패 지점 하나**가 늘었다. "브로커가 죽는다" 는 브로커를 안 쓰면 없는 문제다.

결정적인 것은 이것이다 — **`I-11`(알림 실패가 거래 · 채팅을 막지 않는다)을 지키는 것은 큐가 아니다.**
커밋 후에 전달하고 실패를 흡수하는 것이 지킨다. 큐를 빼도 불변식은 그대로 유지된다.

## 결정

### 1. 전달 수단 — 스프링 애플리케이션 이벤트

`chat` · `trade` 는 `ApplicationEventPublisher` 로 `common.event.NotificationMessage` 를 던진다.
`notification` 이 그 이벤트를 구독해 저장한다.

**의존 방향은 그대로다.** `common` 은 아무 계층도 import 하지 않고, 어떤 도메인도 `notification` 을
import 하지 않는다 (`architecture.md` `[G]`). 지금까지 RabbitMQ 가 하던 간접층을 스프링 이벤트가 대신한다.
그래서 발행하는 쪽에서 `NotificationService` 를 직접 부르지 않는다.

### 2. 전달 시점 — 커밋 후, 트랜잭션이 없으면 즉시

```java
@TransactionalEventListener(phase = AFTER_COMMIT, fallbackExecution = true)
```

`fallbackExecution = true` 가 **두 경로를 한 리스너로** 받는다.

| 경로 | 트랜잭션 | 언제 전달되나 |
|---|---|---|
| `trade` 예약 · 해제 · 거래완료 | 있다 | 커밋 후 |
| `chat` 메시지 전송 | **없다** (`ADR-0005` 로 유니크 위반을 저장 트랜잭션에 가두려고 뺐다) | 즉시 |

이 플래그가 빠지면 트랜잭션이 없는 채팅 경로에서 **이벤트가 조용히 버려진다.** 테스트로 단언한다.

`ADR-0009` 의 「커밋 후」 판단은 그대로 간다 — 커밋 전에 전달하면 롤백된 거래의 알림이 나간다.
틀린 알림이 유실보다 나쁘다.

### 3. 리스너는 `REQUIRES_NEW` 로 새 트랜잭션을 연다

**`AFTER_COMMIT` 리스너 안에서 그냥 저장하면 조용히 사라진다.** 커밋은 끝났지만 트랜잭션 자원은
아직 스레드에 묶여 있어서, 기본 전파(`REQUIRED`)로 저장하면 **이미 완료된 트랜잭션에 합류**한다.
INSERT 가 커밋될 곳이 없다. RabbitMQ 를 쓸 때는 소비자가 다른 스레드에서 새 트랜잭션으로
저장해 이 문제가 없었다.

그래서 리스너에 `@Transactional(propagation = REQUIRES_NEW)` 를 건다.
트랜잭션이 없는 채팅 경로에서는 그냥 새 트랜잭션이 하나 열릴 뿐이라 같은 코드로 동작한다.
`NotificationFlowIntegrationTest` 의 「트랜잭션이 있는 경로」 단언이 이 자리를 지킨다.

### 4. 저장은 동기 · 실패는 리스너가 흡수

리스너가 `try-catch` 로 저장 실패를 삼키고 로그만 남긴다. `@Async` 는 쓰지 않는다 —
INSERT 한 건에 스레드풀 설정과 예외 처리를 더할 값이 없다.

## 대안

- **유지(RabbitMQ)** — `PRD` 의 「비동기 · 메시징」 목표 때문에 안고 가는 선택지였다. 그 목표를
  함께 뺐다. 과설계를 안고 가는 것보다 **걷어낸 판단을 기록으로 남기는 쪽**이 낫다고 봤다
- **`@Async` 스레드풀** — 응답 지연까지 없애지만 지금 지연이 INSERT 한 건이라 값이 없다
- **아웃박스** — 유실을 막지만 테이블 · 폴링 · 수신 멱등 비용. 알림 하나를 잃는 비용이 싸다는
  `ADR-0009` 의 판단은 유지한다 (채팅 원본은 DB 에 있고 목록 API 로 다시 본다)
- **Redis Pub/Sub** — 이미 쓰고 있지만 큐가 아니다. 이 결정에선 브로커 자체를 빼므로 해당 없다

## 결과

- **대가 1** — 커밋과 전달 사이에 서버가 죽으면 알림 하나가 유실된다. `ADR-0009` 와 같다.
  범위는 오히려 줄었다. 브로커 다운 · 소비 실패 · 무한 재배달이 사라진다
- **대가 2** — `ADR-0007` 이 「멀티 서버 채팅 팬아웃은 `ADR-0009` 의 RabbitMQ STOMP 릴레이로 얻는다」 고
  적은 전제가 사라진다. **채팅 멀티 서버가 필요해지면 그때 브로커를 고른다.** 지금 쓰지 않는 브로커를
  미래를 위해 띄워 두지 않는다
- **대가 3** — 처리가 무거워지면(외부 푸시 · 이메일) 다시 큐가 필요하다. `NotificationMessage` 계약을
  그대로 두어, 그때 리스너만 발행기로 바꾸면 되게 한다
- `T-44`(DLQ · 재시도 상한)는 **폐기**한다. 큐가 없으면 재배달도 DLQ 도 없다
- `QA-01` · `QA-02` 의 브로커 측정 기록은 지우지 않는다. 그때의 측정이고, 이 결정의 근거다
