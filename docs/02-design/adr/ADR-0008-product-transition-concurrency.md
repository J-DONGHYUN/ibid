# ADR-0008 상품 상태 전이의 동시성 제어

- 상태: 채택 (`EXP-01` 측정 후, `T-20`)
- 관련: `I-12` · `TR-01` · `TR-02` · `TR-03` · `EXP-01`

## 맥락

한 상품의 상태를 바꾸는 요청이 동시에 들어온다.

- 판매자가 두 채팅방에서 서로 다른 상대를 거의 동시에 예약한다 (두 탭 · 두 기기)
- 예약 해제와 거래완료가 동시에 들어온다

둘 다 "판매중"을 읽고 각자 바꾸면, 나중에 저장한 쪽이 앞의 결과를 덮는다(Lost Update).
예약 상대가 바뀌었는데 먼저 예약된 사람에게 알림이 가는 식으로 어긋난다.

## 선택지

| | 비관적 락 (`SELECT … FOR UPDATE`) | 낙관적 락 (`@Version`) | 조건부 UPDATE |
|---|---|---|---|
| 방식 | 읽을 때 행을 잠근다 | 저장할 때 버전이 바뀌었으면 실패 | `UPDATE … WHERE status = '판매중'` 영향 행 수로 판정 |
| 충돌 시 | 뒤 요청이 기다렸다가 바뀐 상태를 보고 실패 | 뒤 요청이 예외 → 409 | 뒤 요청이 0행 → 409 |
| 비용 | 락 대기 · 데드락 주의 | 재시도 여부를 정해야 함 | 전이 규칙이 엔티티가 아니라 쿼리에 들어간다 |

## 결정 기준

- 이 제품에서 한 상품에 대한 동시 전이는 **드물다.** 드문 충돌에 락 대기 비용을 늘 치를지
- 전이 규칙을 엔티티(`Product`)에 두기로 했다(`ADR-0006`). 조건부 UPDATE 는 이 결정과 충돌한다
- **추측으로 고르지 않는다.** 세 방식을 같은 동시성 테스트로 돌려 결과를 `05-records/experiments/` 에 남기고 고른다

## 결정

**낙관적 락(`@Version`)을 쓴다.** `EXP-01` 에서 두 방식 모두 `I-12` 를 만족했지만,
낙관적이 락 대기가 없어 정상 경로 비용이 0이고 측정에서도 빨랐다(26 vs 62ms, 스레드 20).
이 제품의 동시 전이는 드물어 비관적 락의 상시 대기 비용이 손해다. 전이 규칙은 엔티티의
`reserve()`·`complete()` 등에 그대로 둔다.

- **대가**: 낙관적은 실패가 두 갈래(버전 충돌 `OptimisticLockingFailureException` · 전이 가드
  `BusinessException`)다. 전역 예외 핸들러에서 `OptimisticLockingFailureException → 409` 로
  매핑해 흡수한다(예약 유스케이스 `T-21`).
- 조건부 UPDATE 는 전이 규칙이 쿼리로 새어 `ADR-0006` 과 충돌하므로 측정 전에 제외했다.
