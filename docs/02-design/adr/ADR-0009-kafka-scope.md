# ADR-0009 Kafka 도입 범위와 이벤트 발행 시점

- 상태: **제안** — `NT-01` 구현 전에 결정한다
- 관련: `I-11` · `NT-01` · `NT-02` · `ADR-0007`

## 맥락

메시지를 보내면 알림도 가야 한다. 그런데 알림이 늦거나 실패했다고 **메시지 전송이 실패하면
안 된다**(`I-11`). 둘을 한 트랜잭션에 넣으면 알림 장애가 채팅 장애가 된다.

반대로 떼어 놓으면 새 문제가 생긴다.

- 트랜잭션 **커밋 전에** 이벤트를 발행하면, 롤백된 메시지의 알림이 나간다
- 커밋 **후에** 발행하면, 커밋과 발행 사이에 서버가 죽을 때 알림이 사라진다

## 정해야 할 것

1. **Kafka 로 무엇을 흘리나** — 알림 이벤트만 / 채팅 팬아웃까지 (`ADR-0007`)
2. **언제 발행하나**

| | 커밋 후 발행 (`@TransactionalEventListener(AFTER_COMMIT)`) | 아웃박스 |
|---|---|---|
| 방식 | 커밋이 끝난 뒤 Kafka 로 보낸다 | 같은 트랜잭션에 이벤트 행을 저장하고, 별도 발행기가 읽어 보낸다 |
| 유실 | 커밋과 발행 사이 장애 시 유실 | 유실 없음 (최소 한 번) |
| 비용 | 작다 | 테이블 · 발행기 · 중복 수신 처리 |

## 결정 기준

- **알림 하나를 잃는 것이 얼마나 비싼가.** 채팅 메시지 자체는 DB 에 있고 목록 API 로 다시 볼 수 있다
- 아웃박스를 고르면 수신 측이 같은 이벤트를 두 번 받을 수 있다. 수신 측 멱등 처리가 같이 따라온다
- 도구를 늘리기 전에 필요를 확인한다 — Kafka 없이 무엇이 부족한지를 먼저 적는다

## 결정

미정.
