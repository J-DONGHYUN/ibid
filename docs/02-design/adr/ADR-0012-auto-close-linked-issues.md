# ADR-0012 머지 후 연결된 이슈 닫힘을 GitHub Action 으로 보장한다

- 상태: 채택
- 관련: `04-harness/loop.md` 「상태는 루프만 바꾼다」 · `INC-05` · 백로그 T-32 · T-34 · T-35

## 맥락

루프는 이슈 하나 = 브랜치 하나 = PR 하나로 돈다. 백로그 `✅` 와 이슈 닫힘은 같은 순간에 맞춰져야
갈라지지 않는다 (`loop.md` 「상태는 루프만 바꾼다」). 그래서 PR 본문에 `Closes #N` 을 넣어 머지 시
GitHub 이 이슈를 닫게 했다 (T-32).

그런데 이게 **비결정적으로 샌다.** GitHub 은 PR 본문의 닫기 링크를 **비동기로** 등록하는데, 그게
머지 전에 끝난다는 보장이 없다. 2026-09-30 하루에 PR #83(→#82) · #85(→#84) 가 연달아 열린 채로
남았다 — 같은 형식의 #79(→#77) · #81(→#80) 은 닫혔는데도. `closingIssuesReferences` 가 실패한 PR
에서만 비어 있었다 (`INC-05` 재발).

T-34 가 **절차 안전망**을 더했다 — 루프가 다음 티켓 [0] 에서 직전 머지 PR 의 이슈가 닫혔는지 보고
안 닫혔으면 닫는다. 하지만 이건 **다음 티켓이 시작돼야** 돈다. 방금 머지한 PR 자신은 사각지대로 남는다
(T-34 독립 리뷰 🟡). 절차가 아니라 게이트로 닫아야 사각지대가 사라진다.

## 결정

**PR 이 `main` 에 머지되는 시점에 GitHub Action 이 본문의 닫기 키워드를 읽어 열린 이슈를 닫는다.**
`Closes` 자동 닫힘은 그대로 두고, 그 위에 서버사이드 게이트를 겹친다.

- 트리거: `pull_request: types: [closed]`, `if: merged == true` (base `main`)
- 본문에서 `Closes|Close|Closed|Fixes|Fixed|Resolves|Resolved #N` (대소문자 무시)을 뽑아, 열려 있는 것만 `gh issue close`
- 최소 권한: `issues: write` · `contents: read`
- 멱등: 이미 닫힌 이슈는 건드리지 않는다

## 기준

- **모든 머지 경로를 덮는가** — 웹 UI · CLI · 자동 머지 어느 쪽으로 머지해도 돈다
- **사람 · 다음 티켓에 안 기대는가** — 머지 그 자체가 방아쇠여야 사각지대가 없다
- **최소 권한 · 되돌리기 쉬운가** — 워크플로 한 파일, 지우면 원상복구

## 대안

- **Stop 훅 (로컬)** — 에이전트가 끝낼 때 `gh` 로 직전 머지 PR 을 확인·닫는다. 새 인프라·권한이 없다.
  하지만 사람이 웹에서 머지하고 에이전트를 안 돌리면 안 돈다 — T-34 사각지대를 못 메운다. 기각.
- **예약 점검 (cron / routine)** — 주기적으로 머지됐는데 열린 이슈를 쓸어 닫는다. 모든 경로를 덮지만
  예약 인프라가 필요하고 닫힘까지 지연이 있다. Action 보다 무겁고 느리다. 기각.
- **아무것도 안 하고 T-34 절차만 유지** — 사각지대(방금 머지한 PR)가 남는다. `INC-05` 가 그 자리에서 났다. 기각.

## 결과

- 자동 닫힘이 세 겹이 된다 — ① GitHub `Closes`(불안정) → ② 이 Action(머지 시점 게이트) → ③ T-34 절차([0] 확인).
  Action 이 주력, `Closes` 와 절차는 보조.
- **같은 저장소 브랜치의 `pull_request` 이벤트는 PR 브랜치(머지 커밋) 버전의 워크플로로 돈다** — base(`main`) 가 아니다
  (`pull_request_target` 이나 포크 PR 과 다르다). 그래서 이 워크플로를 추가한 PR 자신의 머지에서도 돈다. 실제로
  T-35(PR #87) 머지에서 이 Action 이 실행돼(run success) `Closes #86` 의 #86 을 닫았다 — GitHub 의 `Closes`
  자동 닫힘(`closingIssuesReferences` 비어 있었다)이 아니라 Action 이 닫은 것으로 첫 실전 검증이 됐다.
