# ADR-0005 동시 요청의 중복은 DB 유니크 제약으로 막고 409 로 응답

- 상태: 채택
- 관련: `I-06` · `I-07` · `I-10` · `PD-07` · `CH-01` · `CH-02`

## 맥락

찜하기는 "이미 찜했는지 확인 → 없으면 저장" 순서다. 같은 요청이 동시에 두 번 오면
둘 다 "없음"을 보고 둘 다 저장하려 한다(check-then-act). 채팅방 열기 · 메시지 재전송도 같다.

## 결정

- **중복의 최종 방어는 DB 유니크 제약이다.** 애플리케이션의 존재 확인은 흔한 경우를 빨리
  돌려주는 지름길일 뿐, 정확성을 보장하지 않는다
- 제약 위반(`DataIntegrityViolationException`)은 **서비스에서 잡지 않고** 전역 핸들러가 409 로 바꾼다
- 멱등이어야 하는 요청(채팅방 열기 · 메시지 재전송)은 409 대신 **기존 것을 돌려준다.**
  이 경우만 서비스가 위반을 잡고 기존 행을 다시 읽는다

## 대안

- **락으로 직렬화** — 행이 아직 없어서 잠글 대상이 없다. 테이블 락은 과하다
- **Redis 분산 락** — 인프라 의존이 하나 늘고, 락이 풀린 뒤의 틈은 결국 DB 가 막아야 한다

## 결과

- 동시성 테스트(여러 스레드가 같은 요청)로 "하나만 남는다"를 검증한다. 단일 스레드 테스트로는 이 결정을 검증할 수 없다
- 프론트는 409 를 받으면 상태를 다시 조회한다
