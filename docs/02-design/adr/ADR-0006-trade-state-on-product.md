# ADR-0006 거래 상태는 상품에 두고, 거래 흐름은 `trade` 가 조율한다

- 상태: 채택
- 관련: `TR-01` ~ `TR-05` · `I-01` ~ `I-04` · `NG-03` · `NG-04`

## 맥락

직거래에서는 게시글 하나가 물건 하나다(`NG-03`). 주문서도 결제도 없다(`NG-04`).
대신 판매자가 채팅 상대 중 한 명을 예약 · 거래완료 상대로 지정한다.

이때 두 가지를 정해야 한다.

1. 거래 상태를 어디에 저장하나
2. "예약 상대는 채팅 상대여야 한다"(`I-04`)는 상품과 채팅방을 **둘 다** 봐야 판정할 수 있다.
   이 판정을 누가 하나

## 결정

1. **거래 상태는 `Product` 에 둔다.** `status` · `reservedBuyerId` · `soldBuyerId`.
   전이 규칙(`I-01` ~ `I-03`)은 `Product` 의 메서드가 막는다
2. **거래 흐름은 새 도메인 `trade` 의 application 이 조율한다.** `trade` 가 채팅방을 조회해
   `I-04` 를 확인한 뒤 `Product` 의 전이 메서드를 부른다. 판매 · 구매 내역 조회도 `trade` 에 둔다

```
trade ──▶ chat ──▶ product
  └───────────────▶ product
```

`chat` 은 채팅방을 열 때 상품의 판매자 · 상태를 봐야 하므로 `product` 에 의존한다.
그래서 **`product` 가 `chat` 을 보면 순환이 생긴다.** 둘을 모두 보는 판정은 한 층 위의 `trade` 로 올린다.

## 대안

- **`Order` · `Deal` 엔티티를 따로 둠** — 물건 하나에 거래 하나라서 상품과 1:1 이다.
  상태가 두 곳에 생기고 둘을 맞추는 일이 생긴다
- **`product` 서비스가 채팅방을 직접 조회** — `product` ↔ `chat` 순환 의존. 에이전트가 가장
  쉽게 택하는 방법이라 명시한다

## 결과

- [G] `product` 는 `chat` · `trade` 를 import 하지 않는다. `chat` 은 `trade` 를 import 하지 않는다
- 거래 이력(누구와 몇 번 예약했다 해제했는지)은 남지 않는다. 필요해지면 이벤트 기록으로 푼다
