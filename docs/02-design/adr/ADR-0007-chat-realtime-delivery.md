# ADR-0007 채팅 실시간 전달 방식

- 상태: 채택 (`T-14`)
- 관련: `CH-02` · `CH-03` · `NT-01` · `ADR-0002` · `ADR-0009`

## 맥락

상대가 채팅방에 접속해 있으면 새로고침 없이 메시지를 받아야 한다(`CH-03`).
서버가 여러 대일 때 보낸 사람과 받는 사람이 **다른 서버에 붙어 있을 수 있다.**
연결이 끊겼다 다시 붙는 동안 온 메시지를 잃으면 안 된다.

## 선택지

| | WebSocket (+ STOMP) | SSE + 전송은 REST |
|---|---|---|
| 방향 | 양방향. 전송도 같은 연결로 | 서버 → 클라이언트 단방향. 전송은 `POST` |
| 인증 | 연결(핸드셰이크) 시 토큰 검증. 연결 중 만료 처리가 따로 필요 | 요청마다 기존 인증 흐름 그대로 |
| 재연결 · 유실 | 직접 구현 (마지막 수신 id 로 재요청) | `Last-Event-ID` 가 표준에 있다 |
| 멀티 서버 팬아웃 | 외부 브로커 필요 (Redis · Kafka) | 같음 |
| 멱등 전송 (`CH-02`) | 메시지 프레임에 식별자 | `POST` 본문에 식별자 |

## 결정 기준

- 전송 경로가 REST 이면 인증 · 검증 · 에러 응답을 기존 체계 그대로 쓴다
- 팬아웃을 Kafka 로 할지 Redis Pub/Sub 으로 할지는 `ADR-0009` 와 함께 정한다
- **채팅은 이 프로젝트의 핵심 기능이므로, 고르지 않은 쪽과의 차이를 설명할 수 있어야 한다**

## 결정

**WebSocket(+STOMP)을 쓴다.** 수신·전송을 한 양방향 연결로 처리한다. 채팅은 이 제품의
핵심 기능이고, STOMP 의 토픽 구독(`/topic/room.{id}`)·전송(`/app/...`)으로 방 단위 라우팅을
표준적으로 얻는다.

- **인증**: 핸드셰이크 때 토큰을 검증한다(`ADR-0002`). 연결 중 토큰 만료 처리는 구현에서 정한다
- **재연결·유실**: 클라이언트가 마지막 수신 메시지 id 로 재요청해 메운다(`CH-03` · `CH-04` 커서 조회 재사용)
- **멱등 전송(`CH-02`)**: 메시지 프레임에 클라이언트 메시지 식별자를 싣는다

SSE+REST 와의 차이: SSE 는 수신이 단방향이라 전송을 별도 REST 로 두고 `Last-Event-ID` 표준
재연결을 공짜로 얻지만, 양방향 상호작용(타이핑·읽음 등 확장)이 한 연결로 안 되고 연결이 둘로
갈린다. 채팅 중심 제품이라 단일 양방향 연결의 WebSocket 을 택한다.

- **팬아웃 브로커(멀티 서버)는 여기서 정하지 않는다.** Redis Pub/Sub 과 Kafka 중 선택은 `ADR-0009`
  (Kafka 도입 범위)와 함께 정한다 — 알림 이벤트 발행과 브로커를 공유할지에 묶이기 때문. 단일 서버
  MVP 는 브로커 없이 시작할 수 있고, 멀티 서버로 갈 때 `ADR-0009` 에서 브로커를 정한다.
