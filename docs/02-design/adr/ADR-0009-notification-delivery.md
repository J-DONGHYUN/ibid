# ADR-0009 알림 전달 방식 (RabbitMQ)

- 상태: **채택** (2026-10-02, 사람) — RabbitMQ · 알림 이벤트만 · 커밋 후 발행
- 관련: `I-11` · `NT-01` · `NT-02` · `ADR-0007`

## 맥락

메시지를 보내면 알림도 가야 한다. 그런데 알림이 늦거나 실패했다고 **메시지 전송이 실패하면
안 된다**(`I-11`). 둘을 한 트랜잭션에 넣으면 알림 장애가 채팅 장애가 된다.

반대로 떼어 놓으면 새 문제가 생긴다.

- 트랜잭션 **커밋 전에** 이벤트를 발행하면, 롤백된 메시지의 알림이 나간다
- 커밋 **후에** 발행하면, 커밋과 발행 사이에 서버가 죽을 때 알림이 사라진다

정해야 할 것이 셋이었다 — (1) 어떤 브로커, (2) 무엇을 흘리나, (3) 언제 발행하나.

## 결정

### 1. 브로커 — RabbitMQ (Kafka 아님)

알림은 **이벤트 하나를 소비자에게 흘리는 pub/sub·작업 큐 문제**다. Kafka 의 강점(대용량 스트림·
보존·재생·이벤트 소싱)은 이 규모(동네 직거래 토이)에서 쓰이지 않는다. RabbitMQ 가 문제에 맞고
운영이 가볍다. 더해, RabbitMQ 는 **Spring STOMP 릴레이**로 채팅 실시간 팬아웃(`ADR-0007` 이 미뤄둔
멀티 서버 숙제)까지 한 브로커로 확장할 여지가 있다.

### 2. 범위 — 알림 이벤트만

`NT-01`·`NT-02` 알림 이벤트만 RabbitMQ 로 흘린다. **채팅 실시간은 지금처럼 인메모리 SimpleBroker**
로 둔다(단일 서버). 채팅 멀티 서버 팬아웃(SimpleBroker → RabbitMQ STOMP 릴레이 교체)은 필요해질 때
**별도 티켓**으로 한다 — 그때 이 브로커를 공유한다.

### 3. 발행 시점 — 커밋 후 (`@TransactionalEventListener(AFTER_COMMIT)`)

메시지/거래 트랜잭션이 **커밋된 뒤** 리스너가 RabbitMQ 로 발행한다. 아웃박스는 쓰지 않는다.

- `I-11` 충족: 발행을 트랜잭션 밖(AFTER_COMMIT)에 둬, 알림 발행 실패가 메시지 전송을 롤백하지 않는다.
- 커밋 전 발행이 아니므로 롤백된 메시지의 알림은 나가지 않는다.

## 대안

- **Kafka** — 재생·대용량이 필요 없고 운영이 무겁다. 과설계라 기각.
- **Redis Pub/Sub** — 이미 쓰지만(조회수) 유실·순서 보장이 약하고 큐 영속이 없다. 알림 큐로는 RabbitMQ 가 낫다.
- **아웃박스** — 유실이 없지만 테이블·발행기·수신 멱등 비용이 든다. **알림 하나를 잃는 비용이 싸다**(채팅
  메시지 원본은 DB 에 있고 목록 API 로 다시 본다). 이 규모에선 커밋 후 발행이 이득이다. 신뢰성이
  문제가 되면 아웃박스로 바꾸는 새 ADR 을 쓴다.

## 결과

- **대가**: 커밋과 발행 사이 장애 시 알림 하나가 유실될 수 있다(드물고, 치명적이지 않다).
- 새 인프라 **RabbitMQ** 를 추가한다 (이 ADR 이 근거). 구현은 `T-25`.
- 발행은 `AFTER_COMMIT` 리스너에서 — 트랜잭션 경계 밖. 알림 소비 실패가 원 트랜잭션에 영향을 주지 않는다.
- 채팅 팬아웃을 나중에 RabbitMQ STOMP 릴레이로 할 때 이 브로커를 공유한다 (`ADR-0007`).
