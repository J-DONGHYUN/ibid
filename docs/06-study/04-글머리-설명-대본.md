## 1. 동시 예약 중복 문제를 락 2종 측정 후 낙관적 락으로 해결, 20명 동시에도 1명만 성공

`PR #123` · `ADR-0008` · `EXP-01`

### 20초 답변

> 한 상품에 구매 희망자가 여러 명 붙는데, 예약은 판매자가 그 중 한 명을 고르는 기능입니다.
> 판매자가 두 탭에서 거의 동시에 다른 사람을 예약하면 두 요청이 둘 다 "판매중"을 읽어서
> 둘 다 통과하고, 나중 요청이 앞사람 예약을 덮어쓰는 문제가 있었습니다.
>
> 낙관적 락과 비관적 락을 둘 다 만들어서 20스레드 동시 테스트로 비교했습니다.
> 정확성은 똑같이 1건만 성공했고, 소요 시간이 26ms 대 62ms로 갈렸습니다.
> 비관적은 요청들이 행 락에 줄을 서기 때문입니다.
> 이 서비스는 동시 예약이 드물어서, 평소에 락 비용을 내지 않는 낙관적 락을 택했습니다.

### 배경 — 왜 생긴 문제인가

한 상품에 구매 희망자가 여러 명 붙고, 각자 판매자와 1:1 채팅을 한다.
예약은 판매자가 그 중 한 명을 고르는 행위다.

예약 처리는 "읽고 → 판단하고 → 쓴다" 세 단계다.
두 요청이 겹치면 둘 다 "판매중"을 읽고 둘 다 가드를 통과한다.
나중에 저장한 쪽이 앞의 결과를 덮는다. Lost Update.

피해는 상태가 깨지는 정도가 아니다.
철수에게 "예약되었습니다" 알림이 나간 뒤에 DB에는 영희가 예약자로 남는다.

### 배경 — 어떻게 골랐나

| | 비관적 락 `SELECT … FOR UPDATE` | 낙관적 락 `@Version` |
|---|---|---|
| 방식 | 읽을 때 행을 잠근다 | 저장할 때 버전이 바뀌었으면 실패 |
| 충돌하면 | 뒤 요청이 기다렸다가, 바뀐 상태를 보고 실패 | 뒤 요청이 예외 → 409 |
| 경합이 없을 때 | 매 요청 락 비용을 낸다 | 비용 0 |

추측으로 고르지 않고 둘 다 코드로 만들어 같은 테스트로 돌렸다(`EXP-01`).
스레드 20개를 대기선에 세워뒀다가 한꺼번에 출발시키고,
출발부터 20건이 전부 끝날 때까지를 쟀다. 1건의 응답시간이 아니라 20건 전부가 끝난 시간이다.

| 방식 | 스레드 | 성공 | 실패 | 소요 |
|---|---|---|---|---|
| 낙관적 | 20 | 1 | 19 | 26ms |
| 비관적 | 20 | 1 | 19 | 62ms |

정확성은 둘 다 통과했다. 갈린 건 비용이다.
20건에서 36ms 차이는 체감될 정도가 아니지만, 비관적은 19개가 줄을 서서 대기가 쌓이는 구조라
요청이 늘수록 벌어진다. 더 결정적인 건 경합이 없을 때의 비용이다.

진 요청은 서버가 재시도하지 않는다. 예약은 "누구를 고르는가"라서 자동 재시도하면
의도하지 않은 사람이 예약될 수 있다. 진 쪽은 409를 받고 클라이언트가 현재 상태를 다시 조회한다.

## 2. 채팅 재전송 시 중복 저장을 DB 유니크 제약·멱등 처리로 해결, 동시 30건에도 1건만 저장

`PR #115` · `ADR-0005` · `ADR-0007` · `CH-02`

### 20초 답변

> 채팅은 받기만 WebSocket으로 밀어주고, 보내기는 REST POST입니다.
> 모바일에서 응답이 끊기면 클라이언트가 같은 POST를 다시 보내는데,
> 서버가 "있는지 확인하고 없으면 저장"하면 두 요청이 겹칠 때 둘 다 "없음"을 보고
> 둘 다 저장돼서 같은 말풍선이 두 개 생깁니다.
>
> 클라이언트가 메시지마다 식별자를 붙이게 하고, (채팅방, 식별자)에 DB 유니크 제약을 걸었습니다.
> 애플리케이션에서 하는 조회는 흔한 경우를 빨리 돌려주는 지름길일 뿐이고, 최종 방어는 DB입니다.
>
> 다만 재전송은 에러가 아니라 성공이어야 해서, 제약 위반이 나면 409 대신 기존 메시지를
> 다시 읽어 돌려줍니다. 30스레드가 같은 식별자로 동시에 보내도 저장은 1건, 실패는 0건입니다.

### 채팅 구조

```
                      ┌─────────────────────────┐
   철수 ──REST POST──▶ │  서버                    │
   (보내기)             │   저장 → 메시지 브로커    │
                      └───────────┬─────────────┘
                                  │  STOMP  MESSAGE
                                  │  (WebSocket 통로)
                                  ▼
                             영희 (받기)
                   미리 SUBSCRIBE /topic/room.7 해둠
```

| | |
|---|---|
| WebSocket | 통로. 핸드셰이크 한 번 하면 계속 열려 있다 |
| STOMP | 그 통로에서 쓰는 규약. `SUBSCRIBE` · `MESSAGE` |
| 메시지 브로커 | 구독자 명단을 보고 배달한다 |

### 어떤 문제인가

```
  ㉮ 응답이 끊겨 클라이언트가 다시 보낸다
  ────────────────────────────────────────────────
   철수 폰                     서버             DB
     │ POST "7시에 봬요" (c-1)    │              │
     ├─────────────────────────▶│ ── INSERT ──▶│  행 1개
     │   ✗ 지하철 진입 — 응답 유실  │              │
     │ ⏱ 타임아웃 → "전송 실패"     │              │
     │ POST "7시에 봬요" (재전송)   │              │
     ├─────────────────────────▶│ ── INSERT ──▶│  행 2개 ✗
```


1번(예약)과 모양은 같지만 막는 방법이 다르다.
예약은 이미 있는 행을 바꾸는 경합이라 그 행에 버전을 걸 수 있었다.
중복 저장은 행이 아직 없는 경합이라 잠글 대상 자체가 없다.

### 왜 유니크 제약으로 풀리나

확인과 저장이 한 동작이 되어 틈이 사라진다.

```
  애플리케이션 조회              DB 유니크 제약
  ─────────────────           ─────────────────
  확인 ── 틈 ── 저장            INSERT 하나로 끝
          ↑                   (제약 위반이 곧 판정)
   다른 요청이 끼어든다              틈이 없다
```

### 식별자는 "말" 이 아니라 "말풍선" 에 붙는다

```
  같은 말풍선의 재시도 — 끊긴 곳은 저장이 아니라 응답이다
  ──────────────────────────────────────────────────────────────
   시간 ─────────────────────────────────────────────────────▶
               t1                 t2                t3

   철수     [ㅋㅋ] c-7 전송      ✗ "전송 실패"      [ㅋㅋ] c-7 재시도
                 │                  ↑                   │
        POST c-7 │                  │ 응답이 못 옴        │ POST c-7
                 ▼                  ╳ ← 에러 지점        ▼
   서버        저장 실행 ────────────┘                이미 있음 → 저장 안 함
                 │                                      │
                 ▼                                      ▼
   DB         c-7  ■ 1건                             c-7  ■ 1건

   철수는 실패로 봤지만 DB 에는 t1 에 이미 저장돼 있었다.
```

**같은 내용을 두 번 보내는 것은 에러가 아니다.** 전송 버튼을 누를 때마다 클라이언트가
새 식별자를 만들기 때문에, "ㅋㅋ" 를 연달아 두 번 쳐도 식별자가 달라서 둘 다 저장된다.
유니크 제약은 내용이 아니라 식별자에 걸려 있다.
막는 것은 "같은 말"이 아니라 **"같은 말풍선의 재시도"** 다.

그래서 서버가 식별자를 만들 수 없다. 재시도인지 또 친 것인지는 클라이언트만 안다.

### 유니크 제약을 어떻게 걸었나

엔티티에 선언한다. 스키마가 `ddl-auto: update` 라 여기 적지 않으면 DB 에 제약이 생기지 않는다.

```java
@Table(
    name = "chat_messages",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_chat_messages_room_client_id",
        columnNames = {"chat_room_id", "client_message_id"})
)
```

```
  chat_messages
  ┌──────────────┬───────────────────┬─────────┐
  │ chat_room_id │ client_message_id │ content │
  ├──────────────┼───────────────────┼─────────┤
  │      7       │       c-7         │  ㅋㅋ    │ ← t1 에 저장된 행
  └──────────────┴───────────────────┴─────────┘
         └─────────────┬─────────────┘
              UNIQUE — 이 묶음은 한 번만

   재시도의 INSERT (7, c-7)  ──▶  ⛔ DB 가 거부
                                   └─▶ 그 행을 다시 읽어 응답에 담는다
```

식별자 하나만 걸면 다른 방이 우연히 같은 id 를 써도 충돌한다. 방 안에서만 유일하면 충분하다.

## 3. 알림 실패가 거래·채팅 요청을 막는 문제를 커밋 후 이벤트·RabbitMQ 발행으로 격리

`PR #139` · `ADR-0009` · `I-11`

### 20초 답변

> 거래완료를 하면 구매자에게 알림도 가야 합니다.
> 그런데 알림 발행을 같은 트랜잭션 안에 두면, 알림이 실패할 때 거래완료까지 롤백됩니다.
> 판매자는 이미 물건을 넘겼는데 "거래완료 실패"가 뜨는 겁니다.
>
> 그래서 발행을 트랜잭션 밖으로 뺐습니다. 트랜잭션 안에서는 스프링 이벤트만 던져두고,
> 커밋이 끝난 뒤에 리스너가 발행합니다. 발행기 자체도 예외를 삼키고 로그만 남깁니다.
>
> 브로커를 내려놓고 테스트하면 거래완료와 메시지 전송은 성공하고 알림만 유실됩니다.
> 알림 하나 잃는 비용이 싸다고 보고 아웃박스는 쓰지 않았습니다.

### 어떤 문제인가

```
  ✗ 알림이 트랜잭션 안에 있을 때
  ──────────────────────────────────────────────────────────────
  판매자 영희              서버                      DB        브로커
      │                    │                        │          ✗ 다운
      │ "거래완료" 클릭       │                        │
      ├───────────────────▶│                        │
      │               ┌────┴───────────────────┐    │
      │               │ 트랜잭션 시작            │    │
      │               │  상품 7 → 거래완료    ────┼───▶│ (커밋 전)
      │               │  알림 발행 ─────────────┼────┼───▶ ╳ 실패
      │               │       ↓ 예외            │    │
      │               │  ⟲ 롤백 ───────────────┼───▶│ 거래완료 취소
      │               └────┬───────────────────┘    │
      │ 500 Server Error   │                        │
      │◀───────────────────┤                        │

   영희 화면 : "거래완료에 실패했습니다"
   DB 상태   : 상품 7 = 판매중        ← 안 팔린 것으로 남는다
   다시 눌러도: 또 500
```

영희는 이미 구매자를 만나 물건을 넘기고 돈을 받았다.
그런데 **알림이 실패했다는 이유로 거래완료를 기록할 수가 없다.**
알림은 거래의 곁가지인데 곁가지가 본체를 막고 있다.

```
  ✅ 발행을 트랜잭션 밖으로 뺐을 때
  ──────────────────────────────────────────────────────────────
  판매자 영희              서버                      DB        브로커
      │                    │                        │          ✗ 다운
      │ "거래완료" 클릭       │                        │
      ├───────────────────▶│                        │
      │               ┌────┴──────────────┐         │
      │               │ 트랜잭션            │         │
      │               │  상품 7 → 거래완료 ─┼────────▶│
      │               └────┬──────────────┘         │
      │                    │ COMMIT ✅ ─────────────▶│ 거래완료 확정
      │                    │                        │
      │                    │ 알림 발행 ───────────────┼──▶ ╳ 실패
      │                    │ (try-catch → 로그만)     │
      │ 200 OK             │                        │
      │◀───────────────────┤                        │

   영희 화면 : "거래완료되었습니다"
   DB 상태   : 상품 7 = 거래완료
   구매자    : 알림만 못 받음 (채팅방 들어가면 보임)
```

차이는 **순서 하나**다. 커밋을 먼저 하느냐, 알림을 먼저 하느냐.

### 어떻게 떼어놨나

```
   거래완료 요청
        │
   ┌────┼───────────────────────────┐
   │ 트랜잭션                        │
   │   상품 상태 전이 → 저장          │
   │   이벤트 던지기 (발행 아직 아님)  │
   └────┼───────────────────────────┘
        ▼  COMMIT ✅   ← 여기서 거래는 이미 끝났다
   AFTER_COMMIT 리스너
        ▼
   발행 ──╳ 실패해도 try-catch 로 삼키고 로그만
        ▼
   큐 ──▶ 소비자 ──▶ 알림 저장
```

| | 무엇 | 막는 것 |
|---|---|---|
| ① | `@TransactionalEventListener(AFTER_COMMIT)` | 발행 실패가 원 트랜잭션을 롤백하는 것 |
| ② | 발행기의 `try-catch` | 발행 예외가 응답까지 올라오는 것 |

### 왜 커밋 "후" 인가

```
   커밋 전에 발행하면          커밋 후에 발행하면
   ─────────────────        ─────────────────
   발행 ──▶ 알림 나감         커밋 ✅
   그 뒤 롤백 ✗              그 뒤 발행
   없던 일의 알림이 간다 ✗      죽으면 알림만 유실 (수용)
```

둘 다 완벽하지 않다. 틀린 알림이 유실보다 나쁘다고 보고 커밋 후를 골랐다.

### 채팅은 왜 `AFTER_COMMIT` 이 없나

2번에서 `send()` 에 `@Transactional` 을 걸지 않았다. 트랜잭션이 없으니 "커밋 후" 도 없다.
저장이 끝난 뒤 발행기를 직접 부르고, `try-catch` 가 유일한 방어다.

| 경로 | 발행 시점 | 방어 |
|---|---|---|
| 거래 (예약 · 거래완료) | 스프링 이벤트 → `AFTER_COMMIT` | ① + ② |
| 채팅 메시지 | 저장 직후 직접 호출 | ② 만 |

### 큐가 꼭 필요한가 — 솔직한 답

**격리를 해주는 것은 큐가 아니라 `AFTER_COMMIT` 과 `try-catch` 다.**
인프라를 안 띄우고도 `I-11` 은 지켜진다.

```
   ① 커밋 후 직접 저장        인프라 0      ← 이 규모의 정답
      커밋 ─▶ AFTER_COMMIT ─▶ 알림 DB 저장 (try-catch)

   ② @Async 스레드풀          인프라 0
      응답 지연까지 없앤다. 서버가 죽으면 처리 중인 것 유실

   ③ 아웃박스 (DB 테이블을 큐로)  인프라 0
      유실 없음. 폴링 비용과 테이블 관리

   ④ 메시지 브로커 (지금)      인프라 +1
```

게다가 **"브로커가 죽는다"는 문제는 브로커를 안 쓰면 없는 문제다.**
큐를 넣어서 실패 지점을 하나 늘렸고, 그걸 막으려고 격리를 한 면이 있다.

큐가 실제로 주는 것: 소비자를 늘릴 자리, 소비자가 내려간 동안 쌓아두기, 재시도.
지금은 소비자가 **하나**뿐이라 과설계에 가깝다.
넣은 이유는 `PRD` 목표 3번(비동기 · 메시징 증명)이 크다. 이 점을 먼저 말하는 편이 낫다.

그래도 `AFTER_COMMIT` + `try-catch` 는 큐를 빼도 필요하다.
알림 저장 로직에 버그가 나도 거래는 지켜져야 하기 때문이다.

### 왜 RabbitMQ 인가

| | Redis Pub/Sub | RabbitMQ | Kafka |
|---|---|---|---|
| 모델 | 방송 | 작업 큐 | 로그 (보존 · 재생) |
| 소비자가 없을 때 | 사라진다 | 큐에 쌓인다 | 보존 기간 동안 남는다 |
| 운영 비용 | 가장 가볍다 (이미 있다) | 가볍다 | 무겁다 |

- **Kafka** — 보존 · 재생 · 대용량 스트림이 강점인데 알림은 하나도 안 쓴다. 운영 부담만 진다.
- **Redis Pub/Sub** — 이미 쓰고 있어 후보였지만, 소비자가 없으면 사라진다.
  알림은 소비자가 가져가 DB 에 저장하는 구조라 **배포로 소비자가 내려간 수십 초의 알림이 통째로 날아간다.**
  (커밋~발행 사이 유실은 밀리초 창이라 성격이 다르다.)
- 덤 — 나중에 채팅 멀티서버 팬아웃을 STOMP 릴레이로 할 때 같은 브로커를 쓴다.

### 아직 없는 것

소비가 계속 실패할 때 재배달을 끊을 장치(DLQ · 재시도 상한)가 없다. `T-44` 결정 티켓이다.
