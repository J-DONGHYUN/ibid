# 루프 설계서

작업 하나가 **어디서 시작해서, 무엇을 거쳐, 언제 끝나는지**와 그 이유를 적는다.
순서와 명령은 `.claude/skills/ticket/SKILL.md` 에 있다. 이 문서는 **왜**만 담는다.

## 한 바퀴

```
사람: "T-04 시작"  (백로그에 없으면 "티켓: 예약 기능 만들자")
  │
[0] 시작      backlog.md 에서 티켓을 찾는다 · 선행이 ✅ 인지 본다
  │           티켓 상세로 이슈를 만든다                      ★ 사람이 정한다 (생성 명령이 승인을 요청)
  │           이슈 브랜치 · 백로그에 🔄 + 이슈 번호           chore/45-remove-legacy
  │
[1] 컨텍스트   요구사항 ID → 검증 기준 → 불변식 → ADR 상태
  │           └ 제안 ADR · NG · 새 갈림길 · 문서와 코드 불일치 → 멈추고 묻는다
  │
[2] 계획      이슈 본문에 🧭 계획 게시                     ★ 사람이 본다 (게시 명령이 승인을 요청)
  │           └ guard-plan.sh: 게시 전에는 src/ 수정 금지
  │
[3] 구현      계획 한 줄 = 커밋 하나                       (커밋 전에 요약 · 메시지를 보여준다)
  │    ▲
  │    │  실패 메시지 = 다음 수정의 컨텍스트
  ▼    │
[4] 게이트    gate-on-stop.sh: 끝내려 하면 architectureTest
  │           └ 3번 연속 실패 → 루프를 멈추고 사람을 부른다
  │
[5] 리뷰 · PR  전체 빌드 → 독립 리뷰 (reviewer 서브에이전트, 이슈 번호 · 브랜치만)
  │           └ 🔴 고친다 · 🟡 고치거나 이유 · ⚪ 적는다
  │           백로그 ✅ → push → PR (🔍 리뷰 · 🔁 루프 기록)  ★ 사람이 본다 (push · PR 이 승인을 요청)
  │
[6] 기록 · 보고 루프가 샜으면 incidents.md → 최종 보고 (머지 전에 볼 곳)
```

## 설계 결정

### 작업 목록은 백로그 문서에, 이슈는 시작할 때

- **무엇이 끝났고 무엇이 남았는지를 한 문서에서 본다** — `docs/01-product/backlog.md`. 마일스톤 표로 단계와 순서, 선행 관계가 한눈에 보인다
- **이슈는 티켓을 시작할 때 만든다.** 티켓 상세(목표 · 완료 조건)가 그대로 이슈 본문이 된다. 이슈는 계획을 게시하고 PR 이 닫는 **작업 기록**이다
- **상태는 루프만 바꾼다.** [0] 에서 `🔄` 와 이슈 번호, [5] 에서 `✅`. 둘 다 이슈 브랜치의 커밋이라 PR 이 `main` 에 머지되는 순간 백로그가 맞춰지고, `Closes` 로 이슈도 닫힌다. 사람이 손으로 바꾸지 않아야 백로그와 이슈가 갈라지지 않는다
  - **`Closes` 자동 닫힘은 보장되지 않는다.** GitHub 이 닫기 링크를 **비동기로** 등록해서, 머지 전에 안 끝나면 이슈가 열린 채 남는다 (`INC-05` 재발 — PR #83 · #85 가 안 닫혔다). 닫힘이 세 겹이다 — ① GitHub `Closes`(불안정) → ② 머지 시점 Action `close-linked-issues.yml`(주력 게이트, `ADR-0012`) → ③ 루프가 다음 [0] 에서 확인(절차 안전망, T-34). 같은 저장소 브랜치의 `pull_request` 는 PR 브랜치 버전으로 돌아서 Action 을 추가한 PR 자신의 머지에서도 돈다 (T-35 #87 에서 실전 검증)
- 설계를 두 번 바꿨다
  1. 처음에는 "진행 상태는 문서에 두지 않고 GitHub Issues 가 정본"으로 정했다. 자주 바뀌는 값을 문서에 적으면 낡는다는 이유였다
  2. 그래서 백로그를 이슈 28개로 미리 만들었는데, **이슈 목록으로는 단계 · 순서 · 선행이 한눈에 보이지 않았다.** 그리고 착수하지 않은 작업까지 이슈로 두면 할 일이 바뀔 때마다 이슈를 고쳐야 했다
  3. 그래서 **목록은 문서로, 이슈는 착수할 때** 로 바꿨다. "문서가 낡는다"는 걱정은 상태를 루프만 바꾸게 해서 막는다

### 시작은 이슈로 한다 — 초안은 에이전트가, 결정은 사람이

- **작업 단위를 정하는 건 사람이다.** 무엇을 할지 정하는 것이 방향이고, 방향은 사람의 몫이다
- 그렇다고 사람이 이슈를 **직접 쓸** 필요는 없다. 사람이 "예약 기능 만들자"라고 말하면 에이전트가 요구사항 문서와 맞춰
  초안(제목 · 요구사항 ID · 완료 조건)을 쓰고, 사람은 **생성 승인**으로 정한다. `gh issue create` 가 `ask` 라서
  승인 요청이 뜨고, 초안 전문이 그 바로 위에 있다. ADR 과 같은 원칙이다 — 초안은 에이전트, 결정은 사람
- 처음에는 "사람이 직접 만든다"로 설계했다가 바꿨다. 이슈 양식을 채우는 일은 요구사항 문서를 찾아 옮기는 일이라
  에이전트가 더 정확하고, 사람은 **범위가 맞는지만** 보면 된다
- 설명이 여러 요구사항에 걸치면 **이슈 하나에 몰지 않는다.** 이슈 하나 = PR 하나라서, 크면 계획도 PR 도 읽을 수 없게 된다
- 이슈가 **계획을 게시할 자리**이자 **PR 이 닫을 대상**이다. 이슈(계획) → 커밋(과정) → PR(결과)이 이어져서, 루프가 실제로 돌았다는 기록이 GitHub 에 남는다
- Jira 를 두지 않는다. 혼자라 연동 자동화가 필요 없다

### 사람의 자리는 셋이다 — 범위 · 계획 · PR

게이트가 판정할 수 있는 것에는 사람을 넣지 않는다. 사람은 게이트가 판정할 수 없는 것만 본다.

- **[0] 범위** — 이 작업을 할지, 이 크기가 맞는지. 이슈 생성 승인
- **[2] 계획** — 방향. **계획이 틀리면 그 뒤가 전부 낭비**라서 가장 먼저, 반드시 본다.
  게시 명령(`gh issue edit`)이 `ask` 라서 승인 요청이 뜨고, 계획 전문이 그 바로 위에 있다
- **[5] PR** — 결과. push · PR 생성이 `ask` 다

**승인을 기다리게 만들지 않는 자리** — [3] 의 커밋. 커밋은 로컬이라 싸다. 보여주고 진행하고, 사람은 이상할 때 끊는다.
커밋마다 승인을 받으면 사람이 붙어 있어야 루프가 돈다.

### 계획 게시를 훅으로 강제한다

`CLAUDE.md` 에 "계획부터 세운다"를 적어 두는 것만으로는 급할 때 건너뛴다. 그래서 **게시 여부**를 파일의 사실로 판정한다 —
이슈 본문에 `## 🧭 계획` 절이 있는가. 승인 여부가 아니라 게시 여부를 보므로 표식 파일도 필요 없고 위조할 것도 없다.

- src/ 가 아닌 파일(문서 · 설정)은 막지 않는다. 컨텍스트를 고치는 일은 계획 없이도 한다
- 통과한 결과만 캐시한다. 게시는 한 방향이라(올린 계획이 사라지지 않는다) 다시 볼 필요가 없고, `gh` 호출은 느리다

### 게이트는 끝내려 할 때 자동으로 돈다

- "코드를 바꿨으면 게이트를 돌린다"를 부탁에서 설정으로 바꾼다. 에이전트가 깜빡해도 돈다
- **빠른 게이트만** 돈다(약 4초). 전체 테스트는 Docker 가 필요하고 1분이 넘어, 끝낼 때마다 돌리면 루프가 느려진다. 전체 테스트는 [5] 에서 한 번, CI 에서 한 번 더
- **src/ · `build.gradle` 이 바뀌지 않았으면 돌리지 않는다.** 문서만 고친 작업을 기다리게 하지 않는다
- 실패 메시지를 **이유 · 위반 위치 중심으로 줄여서** 돌려준다. ArchUnit 의 원래 메시지는 규칙 설명이 앞을 차지해 이유가 뒤로 밀린다

### 3번 연속 실패하면 멈춘다

- 멈춤 조건이 없으면 에이전트는 끝없이 고치거나, 규칙을 우회하는 쪽으로 간다
- 3번이면 같은 방향으로 계속 틀리고 있다는 신호로 본다. **방향이 틀렸거나 규칙이 틀렸다** — 둘 다 사람이 판단할 일이다
- 멈춘 기록(`STOP_FOR_HUMAN`)은 곧 사고 기록 후보다

### 리뷰는 만들지 않은 눈으로 한다

- 첫 루프(T-04)의 잔재(`INC-04`)는 게이트도 통과했고, 루프 안에서는 아무도 못 봤다. **루프 밖에서 따로 부탁한 리뷰**가 찾았다
- 처음 백로그에는 "PR 전에 **자체 리뷰**"로 적었다. 하지만 구현한 에이전트가 자기 diff 를 다시 읽으면 **같은 맥락 · 같은 맹점**으로 읽는다.
  조사를 한쪽으로만 했다면 리뷰도 그쪽만 본다
- 그래서 **리뷰어 서브에이전트**(`.claude/agents/reviewer.md`)를 둔다 (사람이 골랐다). 서브에이전트는 구현 대화를 보지 못한다.
  **넘기는 것을 이슈 번호와 브랜치로 제한**해서, 리뷰어는 이슈(목표 · 완료 조건 · 계획) · 정본 문서 · diff 만으로 판단한다.
  "이 부분을 봐 달라"를 덧붙이지 않는 게 핵심이다 — 덧붙이는 순간 구현자의 관점이 옮겨간다
- **리뷰어는 쓸 수 없다.** 쓸 수 있으면 리뷰 중에 고쳐 버려서 두 번째 구현자가 된다. 지시문으로는 강제되지 않아서
  리뷰어 frontmatter 의 `PreToolUse` 훅(`reviewer-readonly.sh`)이 Bash 를 읽기 명령 화이트리스트로 막는다.
  이 훅은 리뷰어가 도는 동안에만 걸린다. 프로젝트 전체의 `deny` 로 두면 메인 루프까지 막혀서 기각했다
- **전체 빌드 뒤에 부른다.** 게이트가 판정할 수 있는 것을 리뷰어에게 묻지 않는다. 리뷰어의 몫은 게이트가 못 보는 것 —
  완료 조건을 다 채웠나 · 문서와 코드가 맞나 · 조용히 내린 결정이 있나 · 잔재가 남았나
- **발견은 버리지 않는다.** 🔴 는 고치거나 사람에게 묻고, 🟡 는 고치거나 이유를 쓰고, 리뷰어가 틀렸으면 반박으로 남긴다.
  리뷰는 게이트와 달리 **무시할 수 있는 의견**이라서, 무시했는지가 PR 에 보여야 한다

### 끝은 최종 보고로 한다

- T-04 가 끝났을 때 보고는 한 일의 요약뿐이었다. 사람은 PR 을 처음부터 읽어야 무엇을 볼지 알 수 있었다
- 보고 양식을 정한다 — 한 일 · 🔍 리뷰 · 🔁 루프 기록 · **머지 전에 볼 곳**. 마지막 절이 핵심이다.
  게이트도 리뷰어도 판정할 수 없어서 **사람만 볼 수 있는 곳**(스스로 내린 작은 결정 · 반박한 리뷰 · 탐침으로만 확인한 것)을
  에이전트가 1~4개로 골라 준다. [5] PR 에서 사람이 보는 자리를 짧게 만든다

### 루프를 기록한다

- 게이트 결과를 `.git/ibid-loop/<브랜치>.log` 에 남긴다. `.git` 아래라 커밋되지 않고, 브랜치별로 쌓인다
- PR 의 **🔁 루프 기록**이 이걸 읽는다 — 게이트 실패 횟수, 멈춤 여부, 사람 개입, 새로 드러난 결정, 동결 기록 변화
- 이 기록이 쌓이면 **하네스가 나아지는지**를 숫자로 볼 수 있다. 예를 들어 티켓당 게이트 실패 · 사람 개입이 줄어드는가

### 브랜치

```
main ──┬── chore/71-remove-legacy ──PR──▶ main
       └── feat/75-open-chat-room  ──PR──▶ main
```

- 이슈 하나 = 브랜치 하나 = PR 하나. 브랜치 이름이 이슈 번호를 담아야 `guard-plan.sh` 가 계획을 찾는다
- **브랜치는 `main` 하나다.** 티켓 브랜치는 `main` 에서 따고, PR 은 `main` 으로 보낸다
- 처음에는 `develop` → `main` 두 단계로 두었다. 첫 루프(T-04)에서 둘 다 문제가 됐다 (`INC-05`)
  - GitHub 은 기본 브랜치(`main`)로 머지될 때만 `Closes` 로 이슈를 닫는다 → 루프 PR 의 이슈가 하나도 안 닫혔다
  - 저장소를 열면 기본 브랜치의 백로그가 보인다 → `develop` 에서 끝난 티켓이 `main` 에서는 ⬜ 로 보였다
  - `develop` → `main` 을 언제 누가 하는지가 없었다
- `develop` / `main` 을 나누는 건 여럿이 일하며 **배포용 브랜치를 따로 둘 때**의 방식이다. 혼자이고 배포가 없는 지금은
  문제만 만들고 얻는 게 없다. 배포가 생기면 그때 태그나 배포 브랜치를 둔다 — 필요가 확인되기 전에는 늘리지 않는다
- 루프 밖 작업(문서 · 설정)도 브랜치 → PR → `main` 으로 한다. `main` 에 바로 커밋하지 않는다

## 알려진 한계

- **끝내려 할 때마다 게이트가 돈다.** 구현 중간에 사람에게 질문하려고 멈출 때도, src/ 가 바뀌어 있으면 게이트가 돈다.
  짜다 만 코드라 실패하면 질문 대신 수정을 강요받는다. 3회 멈춤이 이걸 끊지만, 질문이 늦어진다
- **계획의 내용은 판정하지 않는다.** 절이 있는지만 본다. 계획이 얕은지는 사람이 [2] 에서 본다
- **리뷰어도 완전히 독립은 아니다.** 같은 저장소 문서를 읽고, 모델도 같다. 문서가 틀렸으면 구현자와 같이 틀린다.
  리뷰어가 무엇을 놓쳤는지는 판정하지 않는다 — 루프 밖 사람 리뷰("PR #○○ 리뷰해줘")를 대신하지 않는다
- **테스트 목록을 다 썼는지는 판정하지 않는다.** `@DisplayName` 의 요구사항 ID 규칙에 게이트가 생기면 "검증 기준마다 테스트가 있는가"를 셀 수 있다
- **머지 뒤 이슈 닫힘 확인은 다음 티켓에 기댄다.** 안전망([0] 의 확인)은 다음 티켓을 시작하거나 사람이 "머지했어" 라고 할 때 돈다. 머지하고 아무 것도 안 하면 확인이 미뤄진다 — 다음 [0] 에서 잡힌다 (T-34)
