# 사고 기록

에이전트가 낸 사고와, 어느 층을 어떻게 고쳤는지를 적는다. 하네스가 나아지는 근거는 여기 쌓인다.

## 층을 고르는 기준

| 증상 | 고칠 층 |
|---|---|
| 요청을 잘못 이해했다 | 프롬프트 — 완료 조건 · 범위를 분명히 |
| 프로젝트 규칙을 몰라서 틀렸다 | 컨텍스트 — `docs/` · `CLAUDE.md` · rules 에 추가 |
| 알면서 어겼다, 반복됐다 | 하네스 — 게이트 · 권한 · 훅으로 강제 |
| 틀렸는데 스스로 못 고쳤다 | 루프 — 실패 메시지 · 단계 · 종료 조건 |

같은 실수가 두 번 나오면 한 층 아래로 내린다.

## 양식

```
## INC-nn 제목
- 날짜 · 작업
- 무슨 일이 있었나
- 왜 — 어느 층이 비어 있었나
- 처방 — 무엇을 어느 층에 더했나
- 재발 — (나중에 채운다) 이후 같은 일이 있었나
```

---

## INC-01 문서에 적은 "현재 위반 수"가 실제보다 적었다

- **날짜 · 작업** — 2026-09-28, `[G]` 규칙을 ArchUnit 게이트로 옮기던 중
- **무슨 일이 있었나** — 컨텍스트 단계에서 에이전트가 `architecture.md` 에 규칙별 "현재 위반"을 grep 으로 세어
  적었다. 게이트를 켜자 문서에 없던 위반이 나왔다 — `common.config.WebConfig` → `auth`,
  `common.config.LocalDataInitializer` → `product` · `user`. grep 을 도메인 폴더끼리의 import 에만 돌리고
  `common` 에서 나가는 방향은 세지 않았다
- **왜** — 컨텍스트 층. 기계가 셀 수 있는 값을 사람(에이전트)이 세어 문서에 옮겨 적었다. 세는 방법이 틀려도
  아무도 모르고, 맞게 세어도 코드가 바뀌면 낡는다
- **처방** — 하네스 층으로 내렸다. **남은 위반의 정본은 동결 기록**(`archunit-store/` · `SourceRulesTest`)이고,
  문서에는 수치를 적지 않고 보는 명령만 적는다 (`harness.md` 「래칫」). `architecture.md` · `code.md` 의 수치를 지웠다
- **재발** —

## INC-02 Stop 훅이 게이트를 한 번도 돌리지 않았다

- **날짜 · 작업** — 2026-09-28, 첫 루프 티켓 T-04 (#71 · PR #72)
- **무슨 일이 있었나** — `gate-on-stop.sh` 는 세션 끝에 한 번, 37ms 만에 끝났다. 게이트(약 4초)를 돌리지 않았고
  `.git/ibid-loop/<브랜치>.log` 도 생기지 않았다. 게이트는 에이전트가 **직접 명령했을 때만** 돌았다
- **왜** — 하네스 층. 훅은 "바뀐 코드가 있나"를 `git status`(커밋 안 된 변경)로 판단했다. 그런데 루프는
  "계획 한 줄 = 커밋 하나"라서 에이전트가 턴을 끝낼 때 작업 트리가 늘 깨끗하다. **"커밋한다"와 "끝낼 때 확인한다"를
  따로 설계해서 둘이 만나는 지점을 놓쳤다.** 결과적으로 게이트는 다시 부탁이 됐다
- **처방** — T-29 (#75). 기준을 "main 과 비교한 이 브랜치의 변경 전체 + 커밋 안 된 변경"으로 바꾸고,
  같은 코드 상태(트리 해시)로 이미 통과했으면 다시 돌리지 않는다. 탐침으로 확인했다
  (`harness.md` 「훅 생존 확인」 T-29 표 — 커밋 뒤 깨끗한 트리에서 게이트가 돈다)
- **재발** —

## INC-03 guard-protected 가 필요 없는 승인을 두 번 요청했다

- **날짜 · 작업** — 2026-09-28, T-04
- **무슨 일이 있었나** — 두 명령이 "보호 파일을 셸로 고친다"로 판정돼 `ask` 가 떴다
  - `./gradlew architectureTest … 2>&1 | tail … wc -l …/archunit-store/…` — `2>&1` 의 `>` 를 파일 쓰기로 봤다
  - `cat > pr-71.md <<'EOF' …` — PR 본문 글에 `archunit-store` 라는 단어가 있었다
- **왜** — 하네스 층. "쓰기 기호가 있나"와 "보호 경로 글자가 있나"를 명령 전체에서 따로 찾았다. **무엇에 쓰는지**를 보지 않았다.
  오탐이 잦으면 사람은 승인을 습관적으로 누르게 되고, 그러면 진짜 위험한 요청도 지나간다
- **처방** — T-30. 리다이렉션(`2>&1` · `>/dev/null`)과 heredoc 본문을 빼고, **쓰기 대상**이 보호 경로인지 본다
- **재발** — T-30 (#80) 을 시작할 때 이 오탐이 한 번 더 났다. 이슈 본문 초안에 `src/` 와 `>` 가 있어
  `gh issue create` 가 `guard-plan` 에 막혔고, 초안을 `Write` 도구로 만들어 우회했다. T-30 이 두 가드를
  `write-target.sh`(쓰기 대상만 본다) 로 바꿔 이 부류를 닫았다. 탐침은 `harness.md` T-30 표

## INC-04 삭제 티켓이 지운 도메인의 공용 잔재를 놓쳤다

- **날짜 · 작업** — 2026-09-28, T-04. 루프 밖 독립 리뷰에서 발견
- **무슨 일이 있었나** — `ErrorCode` 에 주문 6개 · 결제 4개 에러 코드와 섹션 주석이 사용처 없이 남았다.
  완료 조건("다른 코드가 셋을 참조하지 않는다")은 지켰지만 삭제의 목적(잔재 제거)에는 못 미쳤다
- **왜** — 컨텍스트 층. 조사가 **바깥 → 안**(누가 세 도메인을 참조하나)만 봤고, **안 → 바깥**(세 도메인이 쓰던
  공용 코드 · 설정이 남나)은 보지 않았다. 스킬에도 완료 조건에도 그 방향이 없었다
- **처방** — `ticket` 스킬 [1] 에 "지우는 작업은 양방향으로 조사한다"를 더했다. 잔재 정리는 `ErrorCode` 를
  어차피 고치는 T-05 완료 조건에 붙였다. 그리고 루프 안에 리뷰 단계를 둔다 — 자체 리뷰로 적었다가 **독립 리뷰**(리뷰어 서브에이전트)로 바꿨다 (T-31)
- **재발** —

## INC-05 PR 이 머지됐는데 이슈가 닫히지 않았다

- **날짜 · 작업** — 2026-09-28, T-04
- **무슨 일이 있었나** — PR #72 본문에 `Closes #71` 이 있었고 머지됐지만 #71 은 열려 있었다. 백로그는 ✅ 인데
  이슈는 열린 채 — 둘을 함께 맞추려고 만든 규칙(`loop.md` 「상태는 루프만 바꾼다」)이 깨졌다
- **왜** — 루프 층. GitHub 은 **기본 브랜치(main)로 머지될 때만** `Closes` 로 이슈를 닫는다. 루프는 PR 을 develop 으로 보낸다
- **처방** — #71 은 수동으로 닫았다. T-32 (#73) 에서 사람이 **develop 을 없애고 main 하나로** 가기로 정했다.
  티켓 브랜치 → PR → main. 기각한 대안(기본 브랜치를 develop 으로 · 수동 닫기 절차 · GitHub Action)과 이유는 `loop.md` 「브랜치」.
  이 처방이 동작하는지는 #73 이 PR 머지로 **자동으로** 닫히는지로 확인한다
- **재발** — 2026-09-30, T-28. PR #83 이 본문에 `Closes #82` 를 담고 `main` 으로 머지됐는데 #82 가 열린 채 남았다.
  같은 형식의 #79(→#77) · #81(→#80) 은 자동으로 닫혔다 — `closingIssuesReferences` 가 #83 에서만 비어 있었다.
  원인은 develop 이 아니라 **GitHub 이 닫기 링크를 비동기로 등록**하는데 그게 머지 전에 끝난다는 보장이 없다는 것. `Closes` 만으로는 부족하다.
  #82 는 수동으로 닫았고, **T-34** 로 머지 뒤 이슈 닫힘을 루프가 확인하고 안 닫혔으면 닫는 안전망을 더했다 (`ticket` 스킬 [0] · `loop.md` 「상태는 루프만 바꾼다」)
  - **또 재발** — 2026-09-30, T-34. PR #85(→#84) 가 같은 방식으로 안 닫혔다. 두 번 연속이라 이 저장소에서 `Closes` 는 신뢰할 수 없다고 봤다.
    #84 는 T-34 절차([0])로 잡아 수동으로 닫았지만, 절차는 다음 티켓에 기대 사각지대(방금 머지한 PR)가 남는다. **T-35** 로 PR 머지 시점 GitHub Action(`close-linked-issues.yml`, `ADR-0012`)을 두어 게이트로 닫는다

## INC-06 새로 만든 리뷰어를 같은 세션에서 부를 수 없었다

- **날짜 · 작업** — 2026-09-28, T-31 (#77)
- **무슨 일이 있었나** — 리뷰어(`.claude/agents/reviewer.md`)를 만들고 [5] 에서 부르자 `Agent type 'reviewer' not found`.
  Claude Code 는 에이전트 정의를 **세션을 시작할 때** 읽는다. 대신 `general-purpose` 에 리뷰어 지시문을 넣어 부르는 길이 있었지만,
  그러면 frontmatter 의 읽기 전용 훅이 빠져 독립 리뷰의 조건이 깨진다. 쓰지 않고 멈췄다
- **왜** — 루프 층. 읽기 전용은 훅 스크립트에 만든 입력을 넣어 탐침했을 뿐, **실제 경로**(Agent 호출 → frontmatter 훅)로는
  부르지 않았다. 하네스 파일이 **언제부터 적용되는지**(즉시 · 세션 시작)를 설계에 적지 않았다
- **처방** — 스킬 [5] 에 "리뷰어가 없다고 나오면 다른 에이전트로 대신하지 않고 멈춘다"를 더했다. `harness.md` 「알려진 구멍」에
  "리뷰어를 만들거나 고친 티켓은 새 세션에서 [5] 를 이어 한다"를 적었다. T-31 은 새 세션에서 [5] 부터 이어 한다
- **재발** —
