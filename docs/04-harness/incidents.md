# 사고 기록

에이전트가 낸 사고와, 어느 층을 어떻게 고쳤는지를 적는다. 하네스가 나아지는 근거는 여기 쌓인다.

## 층을 고르는 기준

| 증상 | 고칠 층 |
|---|---|
| 요청을 잘못 이해했다 | 프롬프트 — 완료 조건 · 범위를 분명히 |
| 프로젝트 규칙을 몰라서 틀렸다 | 컨텍스트 — `docs/` · `CLAUDE.md` · rules 에 추가 |
| 알면서 어겼다, 반복됐다 | 하네스 — 게이트 · 권한 · 훅으로 강제 |
| 틀렸는데 스스로 못 고쳤다 | 루프 — 실패 메시지 · 단계 · 종료 조건 |

같은 실수가 두 번 나오면 한 층 아래로 내린다.

## 양식

```
## INC-nn 제목
- 날짜 · 작업
- 무슨 일이 있었나
- 왜 — 어느 층이 비어 있었나
- 처방 — 무엇을 어느 층에 더했나
- 재발 — (나중에 채운다) 이후 같은 일이 있었나
```

## INC-01 문서에 적은 "현재 위반 수"가 실제보다 적었다

- **날짜 · 작업** — 2026-09-28, `[G]` 규칙을 ArchUnit 게이트로 옮기던 중
- **무슨 일이 있었나** — 컨텍스트 단계에서 에이전트가 `architecture.md` 에 규칙별 "현재 위반"을 grep 으로 세어
  적었다. 게이트를 켜자 문서에 없던 위반이 나왔다 — `common.config.WebConfig` → `auth`,
  `common.config.LocalDataInitializer` → `product` · `user`. grep 을 도메인 폴더끼리의 import 에만 돌리고
  `common` 에서 나가는 방향은 세지 않았다
- **왜** — 컨텍스트 층. 기계가 셀 수 있는 값을 사람(에이전트)이 세어 문서에 옮겨 적었다. 세는 방법이 틀려도
  아무도 모르고, 맞게 세어도 코드가 바뀌면 낡는다
- **처방** — 하네스 층으로 내렸다. **남은 위반의 정본은 동결 기록**(`archunit-store/` · `SourceRulesTest`)이고,
  문서에는 수치를 적지 않고 보는 명령만 적는다 (`harness.md` 「래칫」). `architecture.md` · `code.md` 의 수치를 지웠다
