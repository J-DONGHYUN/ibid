# 티켓 루프

루프 설계의 이유는 `docs/04-harness/loop.md` 에 있다. 이 스킬은 **순서와 명령**만 담는다.

```
[0] 시작 → [1] 컨텍스트 → [2] 계획 게시 → [3] 구현 ⇄ [4] 게이트 → [5] 리뷰 · PR → [6] 기록 · 보고
                            ▲ 사람이 본다                          ▲ 리뷰어 · 사람이 본다
```

## [0] 시작 — 백로그의 티켓으로 이슈를 만들고 브랜치를 만든다

**작업 목록의 정본은 `docs/01-product/backlog.md` 다.** 이슈는 미리 만들어 두지 않고, 티켓을 시작할 때 만든다.

### 0. 직전 머지를 확인한다 — 이슈가 정말 닫혔나

새 티켓을 시작하기 전에(사람이 "머지했어" 라고 하면 그 자리에서) `main` 을 당기고, 마지막으로 머지한 PR 의
이슈가 정말 `CLOSED` 인지 본다. `Closes #번호` 자동 닫힘은 GitHub 의 **비동기 링크 등록**에 기대서, 머지 전에
안 끝나면 이슈가 열린 채 남는다 — 백로그 `✅` 와 이슈 상태가 갈라진다 (`INC-05`. PR #83 이 그렇게 샜다).

```bash
git switch main && git pull --ff-only
pr=$(gh pr list --base main --state merged --limit 1 --json number -q '.[0].number')
gh pr view "$pr" --json closingIssuesReferences,body -q '{closes: [.closingIssuesReferences[].number], body}'
```

`Closes #번호` 가 본문에 있는데 그 이슈가 `OPEN` 이면 (또는 `closingIssuesReferences` 가 비어 있으면) 직접 닫는다:

```bash
gh issue close <번호> --comment "PR #$pr 에서 완료됐다. Closes 자동 닫힘이 안 걸려 수동으로 닫는다 (INC-05)."
```

자동 닫힘(`Closes`)은 그대로 둔다 — 대부분 동작한다. 이건 샜을 때 잡는 안전망이다.

### 1. 티켓을 찾는다

- **"T-04 시작"** → 백로그에서 `T-04` 를 찾는다
- **"삭제 예정 도메인 지우기 시작"** → 백로그의 제목으로 찾는다. 여러 개가 걸리면 후보를 보여주고 묻는다
- **"#45 시작"** → 이미 만든 이슈다. 이슈 본문의 `백로그: T-nn` 으로 티켓을 찾고, 3 은 건너뛴다
- **백로그에 없는 작업("티켓: 가격 정렬 추가하자")** → 백로그에 **티켓을 새로 추가**한다
  - 알맞은 마일스톤 표에 행을, 「티켓 상세」 에 절을 쓴다. ID 는 가장 큰 번호 + 1
  - `requirements.md` 와 맞춰 요구사항 ID 를 찾는다. 여러 ID 에 걸치면 **티켓 하나에 몰지 않는다** — 나눌지 묻는다
  - `NG` 에 걸리면 추가하지 않고 묻는다

### 2. 시작해도 되는지 본다

- 상태가 `⬜` 가 아니면 멈춘다 (`🔄` 면 이어서 할지, `✅` 면 이미 끝난 것)
- **선행이 모두 `✅` 가 아니면 시작하지 않는다.** 선행 티켓을 먼저 할지 묻는다

### 3. 이슈를 만든다

「티켓 상세」 의 내용을 `.github/ISSUE_TEMPLATE/ticket.md` 양식으로 옮긴다.

- 제목: 상세의 **이슈 제목** 그대로
- 목표 · 완료 조건 · 참고: 상세에서 옮긴다. 목표 맨 위에 `- 백로그: T-nn` 을 적는다
- **계획(`🧭 계획`)은 넣지 않는다.** 계획은 [1] 에서 컨텍스트를 읽은 뒤 [2] 에서 쓴다

**본문 전문을 대화에 먼저 출력한다.** 생성 명령에 승인 요청이 뜨는데, 본문이 그 바로 위에 있어서 사람이 범위를 읽고 누르는 자리가 된다.
작업 단위를 정하는 건 사람이다 — 에이전트는 초안을, 사람은 생성 승인을.

```bash
draft="$(git rev-parse --git-dir)/ibid-loop/issue-draft.md"
mkdir -p "$(dirname "$draft")"   # 본문을 이 파일에 쓴 뒤
gh issue create --title "<이슈 제목>" --body-file "$draft" --label <type>    # type: 제목 접두사 (feat · refactor · chore · test · docs), 결정 티켓은 decision. 출력된 URL 에서 이슈 번호를 얻는다
```

반려되면 무엇을 고칠지 묻고, 백로그의 상세를 고친 뒤 다시 만든다.

### 4. 브랜치를 만들고 백로그에 시작을 적는다

```bash
git switch main && git pull --ff-only
git switch -c <type>/<번호>-<짧은-영문-이름>      # type: 이슈 제목의 접두사
```

백로그의 그 티켓 행에 **상태 `🔄`, 이슈 `#번호`** 를 적고 첫 커밋으로 남긴다 (`docs: T-nn 을 시작한다`).
이 커밋이 PR 에 함께 실려 `main` 에 머지되면 백로그가 갱신되고, `Closes #번호` 로 이슈도 함께 닫힌다.

- 제목에 접두사가 없으면 묻는다. 추측하지 않는다
- 이미 그 브랜치에 있으면 이어서 한다. `.git/ibid-loop/` 의 기록과 이슈의 계획을 먼저 읽는다

## [1] 컨텍스트 — 테스트 목록을 수집한다

산출물은 **이 이슈가 통과해야 할 테스트 목록** 하나다. 설계하지 않고 수집한다.

1. 이슈에서 요구사항 ID 를 찾는다 (`TR-01` · `PD-06` …). 없으면 이슈의 완료 조건을 쓰고, 그것도 모호하면 사람에게 짧게 묻는다 (무엇을 · 범위 · 완료 조건)
2. `docs/01-product/requirements.md` 에서 그 ID 의 **검증 기준**을 옮긴다 → 테스트 목록
3. `docs/02-design/domain-model.md` 에서 그 ID 를 인용하는 **불변식**을 찾는다 → 금지된 전이 · 동시성 테스트를 목록에 더한다
4. 걸린 **ADR** 의 상태를 본다
5. **지우거나 옮기는 작업이면 양방향으로 조사한다** — 누가 대상을 참조하나(바깥 → 안) + 대상이 쓰던 공용 코드 · 에러 코드 · 설정이 남나(안 → 바깥). 한쪽만 보면 잔재가 남는다 (`INC-04`)

그리고 **멈출 곳**을 확인한다. 하나라도 걸리면 [2] 로 가지 않고 사람에게 묻는다.

- 걸린 ADR 이 `제안` 이다 → 선택지와 결정 기준을 정리해 묻는다
- 작업이 `PRD.md` 의 `NG` 에 걸린다 → 묻는다
- **ADR 에 없는 갈림길**이 보인다 (대안이 여럿 · 되돌리기 비쌈 · 흔한 방법이 틀릴 수 있음) → `제안` ADR 초안을 쓰고 묻는다. 결정은 사람이 한다
- 문서와 코드가 다르다 → 어느 쪽이 맞는지 묻는다

## [2] 계획 — 이슈 본문에 게시한다

구현 전에 한다. 방향이 틀렸을 때 고치는 비용이 가장 낮은 순간이다.
**계획이 게시되기 전에는 `src/` 를 고칠 수 없다** (`guard-plan.sh`).

이슈 본문 **끝에** 아래 절을 덧붙인다. 기존 본문은 지우지 않는다.

```markdown
## 🧭 계획

### 읽은 컨텍스트
- 요구사항: TR-01
- 불변식: I-01 · I-04 · I-12
- ADR: ADR-0006 (채택) · ADR-0008 (채택 — ○○ 락)

### 통과해야 할 테스트
- [TR-01] 판매자 본인만 예약할 수 있다
- [TR-01] 서로 다른 두 상대로 동시에 예약해도 한 명만 예약된다
- [I-01] 예약중에서 다시 reserve 하면 실패한다

### 작업 — 한 줄 = 커밋 하나
1. Product 에 reserve · cancelReservation 전이와 전이표 테스트
2. …
3. 리뷰 반영 (있으면) — [5] 독립 리뷰에서 고친 것

### 새로 내려야 하는 결정
- 없음
  - 되돌리기 **비싼** 결정이 있으면 여기서 멈추고 [1] 의 멈출 곳으로 돌아간다 (제안 ADR 초안 → 사람이 정한다)
  - 되돌리기 **쉬운** 결정은 선택과 근거를 여기에 적는다. 계획 승인이 곧 그 결정의 승인이다

### 동결 기록
- 줄어들 것: …   /  늘어날 것: 없음
```

- 작업 목록은 **체크리스트로 만들지 않는다.** 진행은 커밋과 대화에서 보인다
- 게시 전에 **계획 전문을 대화에 먼저 출력한다.** 게시 명령에 승인 요청이 뜨는데, 계획이 그 바로 위에 있어서 사람이 읽고 누르는 자리가 된다

```bash
body="$(git rev-parse --git-dir)/ibid-loop/issue-<번호>.md"
mkdir -p "$(dirname "$body")" && gh issue view <번호> --json body -q .body > "$body"   # 기존 본문
# 위 계획 절을 파일 끝에 덧붙인 뒤
gh issue edit <번호> --body-file "$body"
```

반려되면 무엇을 고칠지 묻고 다시 게시한다.

## [3] 구현 — 계획 한 줄씩

- 순서는 `domain → infra → application → presentation`. 의존 방향대로 쓴다
- 계획 한 줄을 끝낼 때마다 **커밋한다.** 커밋 전에 변경 요약과 커밋 메시지를 보여준다. 승인은 기다리지 않는다
- 한 줄에 커밋이 여러 개 필요하면 계획이 굵은 것이다. 계획을 고쳐 다시 게시한다
- 코드를 바꿀 때마다 `./gradlew architectureTest` 를 돌린다 (약 4초)
- 동결 기록은 **줄이기만 한다.** 동결된 코드를 고쳐 위반이 사라지면 `SourceRulesTest` 목록에서도 지운다

## [4] 게이트 — 끝내기 전에

- 끝내려 하면 `gate-on-stop.sh` 가 `architectureTest` 를 자동으로 돌린다. 실패하면 끝나지 않고 실패 메시지가 돌아온다
- **메시지의 `이유` 와 근거 문서를 읽고 코드를 고친다.** 규칙 · 테스트 · 동결 기록을 고쳐 통과시키지 않는다
- **3번 연속 실패하면 훅이 루프를 멈추고 사람을 부른다.** 그때는 더 고치지 말고, 무엇을 시도했고 왜 막혔는지 보고한다

## [5] 리뷰 · PR — 전체 빌드 → 독립 리뷰 → PR

### 1. 전체 빌드

```bash
AWS_ACCESS_KEY=test AWS_SECRET_KEY=test ./gradlew build    # Docker 필요. 전체 테스트
```

게이트가 판정하는 것은 여기서 끝낸다. 리뷰어는 그것을 다시 보지 않는다.

### 2. 독립 리뷰

리뷰어 서브에이전트(`.claude/agents/reviewer.md`)를 부른다. **넘기는 것은 이슈 번호와 브랜치뿐이다.**
구현 의도 · 고민 · "이 부분을 봐 달라"를 덧붙이지 않는다 — 덧붙이면 만든 눈이 리뷰어에게 옮겨간다.

```
Agent(subagent_type: "reviewer", prompt: "#77 chore/77-independent-review")
```

- **`reviewer` 가 없다고 나오면 다른 에이전트로 대신하지 않는다.** 에이전트 정의는 세션을 시작할 때 읽혀서,
  이 세션에서 리뷰어를 만들거나 고쳤으면 아직 없다. 다른 에이전트는 읽기 전용 훅이 없다. 멈추고 새 세션에서 [5] 를 이어 하자고 한다 (`INC-06`)

돌려받은 결과는 **원문 그대로** `.git/ibid-loop/review-<번호>.md` 에 저장한다. PR 과 최종 보고가 이것을 옮긴다.
그리고 발견마다 조치를 정한다.

| 등급 | 조치 |
|---|---|
| 🔴 | **고친다.** 고치지 않겠다면 이유를 적어 사람에게 묻는다 |
| 🟡 | 고치거나, 고치지 않는 이유를 한 줄 적는다. 이 티켓 밖의 일이면 백로그에 `⬜` 티켓으로 |
| ⚪ | 조치 없이 옮겨 적는다 |

- 리뷰어가 틀렸다고 보면 근거를 적어 **반박**으로 둔다. 조용히 버리지 않는다 — 사람이 머지 전에 볼 곳이 된다
- 고친 것은 커밋한다 (계획의 마지막 줄 "리뷰 반영")
- **🔴 를 고쳤으면 리뷰어를 한 번 더 부른다** (같은 입력, 새 호출). 또 🔴 가 나오면 멈추고 사람에게 묻는다

### 3. 함께 고친다

- **`backlog.md` 의 그 티켓 행 상태를 `✅` 로**, 마일스톤 제목의 완료 수(`— 1 / 5`)를 맞춘다. PR 이 머지되면 완료가 된다
- 루프 중에 새로 드러난 작업이 있으면 백로그에 `⬜` 티켓으로 추가한다 (선행 표시 포함)
- `requirements.md` 의 `상태` 열
- 불변식 · 전이가 바뀌었으면 `domain-model.md`, 결정이 생겼으면 ADR

### 4. PR

```bash
git push -u origin <브랜치>
gh pr create --base main --title "<이슈 제목>" --body-file <본문>    # 본문에 Closes #<번호>
```

PR 본문은 `.github/PULL_REQUEST_TEMPLATE.md` 를 따른다.

- **🔍 리뷰** — 리뷰 원문의 발견마다 한 줄씩, 조치(고침 + 커밋 · 안 고침 + 이유 · 반박 + 근거 · 백로그 T-nn)를 붙인다
- **🔁 루프 기록** — `.git/ibid-loop/<브랜치>.log` 로 채운다.
  **로그 파일이 없으면 "0회" 가 아니라 "기록 없음" 이라고 적는다** — 근거 없는 0 은 기록을 믿을 수 없게 만든다.
  예정에 없던 승인 요청(훅 오탐 등)도 사람 개입으로 센다

```bash
cat "$(git rev-parse --git-dir)/ibid-loop/$(git branch --show-current | tr / _).log"
```

## [6] 기록 · 보고

### 기록 — 루프가 샜으면

아래 중 하나라도 있었으면 `docs/04-harness/incidents.md` 에 기록 초안을 쓰고 PR 에 포함한다.

- 게이트가 루프를 멈췄다 (`STOP_FOR_HUMAN`)
- 사람이 중간에 끊고 방향을 바꿨다
- 문서에 없던 규칙 · 갈림길 때문에 되돌아갔다
- 리뷰어가 🔴 를 찾았다 — 게이트나 컨텍스트가 먼저 잡을 수 있었는지 본다

어느 층을 고칠지는 `incidents.md` 「층을 고르는 기준」 을 따른다.

### 최종 보고 — 루프의 마지막 메시지

PR 을 만든 뒤 **아래 양식으로 끝낸다.** 사람이 이것만 읽고 머지 전에 무엇을 볼지 알 수 있어야 한다.
요약을 늘리지 않는다 — 자세한 것은 PR 에 있다.

```markdown
## T-nn 끝 — PR #○○ (머지 대기)

### 한 일
- <커밋 한 줄 = 한 줄. 계획의 작업 번호와 맞춘다>

### 🔍 리뷰 — 🔴 n · 🟡 n · ⚪ n
- 🔴 <요약> → 고침 (<커밋>)
- 🟡 <요약> → 안 고침: <이유>

### 머지 전에 볼 곳
1. `<파일>:<줄>` — <왜 사람이 봐야 하나>
```

**머지 전에 볼 곳**은 게이트도 리뷰어도 판정할 수 없어서 **사람만 볼 수 있는 곳**이다. 1~4개로 고른다.

- 계획에서 되돌리기 쉽다고 보고 스스로 정한 결정이 코드에 들어간 곳
- 반박한 리뷰 · 고치지 않은 🟡
- 검증을 못 했거나 탐침으로만 확인한 곳 (실제 경로를 못 탄 것)
